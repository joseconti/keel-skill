# Phase 5 — Development

Goal: implement the functional spec (and, if there was UI, the faithful build) into working software, with test points throughout so defects surface early instead of at the end. Work is organized into sprints with a living tracking file and a self-sufficient continuation prompt at each sprint close, so a large project survives across multiple chats without losing context or repeating past mistakes.

## Inputs

- `docs/02-functional-spec.md` (requirements, data model, integrations, acceptance criteria, permissions)
- `docs/03-technical-plan.md` (stack, architecture, code map, conventions, testing, tooling commands — the build follows it; if it must change, update it and record the decision, never silently diverge)
- `docs/flows/*.md` (journeys to implement)
- `docs/BUILD-SPEC.md` (if there was a UI — the faithful build contract; never deviate from it)
- `docs/decisions.md` and `docs/lessons-learned.md` (never re-litigate, never repeat)
- The loaded security profile (`references/security/<type>.md`) — apply throughout, not at the end.
- `references/accessibility.md` and the accessibility decision from `docs/01-discovery.md` — apply throughout, not at the end; if there was UI, also the accessibility spec in the handoff (`SPEC/accessibility.md` / `docs/BUILD-SPEC.md` §4a).

## Principles

- **Implement to the spec, not around it.** If the spec is wrong or incomplete, fix the spec (and, if UI-related, that's a Design Request) — don't silently diverge in code.
- **Reuse internal API; never duplicate code.** Before writing any new function, method, or class, search `docs/api/` and `docs/reference/` (which were started at the beginning of Phase 5 and grow with each slice) for an existing fit. If one exists, reuse it. If one is close but not exact, generalize the existing function (add a parameter, lift the type) rather than create a near-duplicate. A near-duplicate is a defect: it gets refactored, not committed. The codebase has exactly one canonical implementation per behavior.
- **Document every public surface at the moment it changes — created, modified, or removed — not later.** Every function/method/class/hook/action/filter/REST route/MCP ability/CLI command is documented in the right `docs/api/` or `docs/reference/` file as part of the same slice that introduces it, updated there in the same slice that changes it (signature, params, return, errors, permissions, behavior, example), and never silently deleted when it goes — per SKILL.md "Document every public surface at the moment it changes". The slice's test point includes "docs match the as-built code; every touched example runs". Phase 6 consolidates the documentation that exists; it does not write it from zero. The same discipline covers the end-user guide once it exists (`guide/` — created at Phase 6): a slice that adds or changes user-visible behavior updates the guide in the SAME slice, in every locale it carries — nothing user-facing is ever left undocumented "for later".
- **Maximum extensibility for extensible project types.** For WordPress/WooCommerce plugins, MCP servers, and libraries/components, every slice exposes extension points so third parties can override behavior without forking. The default density is: every user-facing string passes through a filter (e.g. WordPress `apply_filters`), every meaningful decision in a flow exposes a `do_action` before and after, every database/query result is filterable before return, every external response (REST, MCP, webhook) is filterable before send, and every public class supports a documented mechanism to be replaced or extended. All extension points are prefixed (the project's namespace), documented in `docs/reference/hooks-and-extension-points.md` at the same slice, and have at least one runnable example.
- **Test points are checkpoints, not a final phase.** After each meaningful unit (a flow, an integration, a permission boundary), stop and verify before continuing — same logic as the one-step-at-a-time external setup: catch the defect where it happened.
- **Right the first time.** Anything a compile/build, a lint pass, booting the playground, or a basic test would have caught is caught BEFORE the slice is handed over — nothing of that class may surface later, in review, at release, or in the user's hands. When such a defect does escape a test point, that is a process defect, not bad luck: record it in `docs/lessons-learned.md` and add the missing check to the test point itself, so the same class of defect cannot escape twice.
- **Tests are never weakened to pass.** A failing test or acceptance criterion is NEVER deleted, skipped, or loosened to make it pass. If the test is genuinely wrong, that is a spec correction: fix the spec first — with its entry in `docs/decisions.md` — and only then the test. Same force as "if the spec is wrong, fix the spec" above; the suite is part of the spec's enforcement, never an obstacle to work around.
- **Real functional verification, not only automated tests.** Whenever the project can be run, the verification playground defined in `docs/03-technical-plan.md` (Docker/docker-compose, wp-env, a playground script, a disposable sandbox — whatever fits the stack) exists from the scaffold onward, and test points include exercising the software in it for real: walk the flow end to end, run the CLI command if one was built, call the API with real requests. Automated tests prove the parts; the playground proves the product. `docs/playground.md` stays current (start/stop commands, access details, step-by-step try-it instructions) so the user can try the current state at any moment.
- **Security profile is live.** Every input boundary, auth path, data write, and external call is checked against the profile as you build it.
- **Accessibility is live, built into every slice.** Every UI slice is built accessible as it is written — semantic/native controls first, accessible name/role/state exposed to the platform accessibility API, keyboard/assistive-tech operability, visible focus and correct focus order, contrast met, adequate target sizes, error identification (not color-only), and honored user preferences (reduced motion, text scaling, high contrast). It is verified at the slice's test point, never deferred. The target is the Phase 1 level (WCAG 2.2 AA floor / AAA where feasible; EN 301 549 / EAA where in scope; the platform's native a11y API). Per `references/accessibility.md`.
- **Project-type structure.** Lay the codebase out per the conventions for the type (WordPress plugin layout, MCP server layout, etc.) — the security profile and Phase 7 depend on a sane structure.
- **Internationalization is a build rule from line one.** If Phase 1 decided multi-language: every user-facing string is externalized through the platform's i18n mechanism, never hardcoded at the use site, never concatenated (use parameterized/placeholder formatting with translator notes, not string addition). The mechanism is platform-specific — do not assume the WordPress pattern is universal:
  - *Function-wrapping model* (WordPress, many web backends): strings wrapped at the use site, e.g. `__()`/`_e()`/`esc_html__()` with the correct text domain; the base locale file (`.pot`) generated from the source strings.
  - *Key/constant model* (native apps — macOS/iOS `.strings` / String Catalogs with `NSLocalizedString`/keys, Android `strings.xml` with `R.string.*`, web frameworks like i18next): code references a stable key/constant and the system substitutes the localized value; the base language is the set of default values bound to those keys in the base catalog.
  In both, the **base language decided in Phase 1** is the source of truth (the literal source strings, or the default values of the keys). That base language is **English by default in every project** — and **always English for WordPress/WooCommerce**, never Spanish-base (per SKILL.md "Output language & internationalization"); write the source strings in English accordingly. The base catalog/locale resource is generated from it and kept current; all other locales are translations derived from it. Pick the idiomatic mechanism for the project's platform/type from Phase 1. If Phase 1 decided single-language, don't scatter a fake i18n layer — but still keep user-facing strings centralized enough that future translation isn't a rewrite. Retrofitting i18n later is a rewrite; that's why the decision was made in Phase 1.
- **Migrations and backward compatibility (if Phase 1 recorded an installed base).** Never assume a clean install. Version the data schema; write migrations that are idempotent and, where feasible, reversible; preserve or transform existing user data, never silently drop it; keep backward compatibility for anything external code or stored config depends on, or provide a documented, gated breaking change. Clean uninstall must not leave sensitive residue unless the user opted in. The upgrade path is tested from the *real previous version*, not only from a clean install — that test point is mandatory.
- **External dependencies fail safe.** For every dependency recorded in Phase 1: pin/check the exact version, and if it's absent or version-incompatible, degrade gracefully (admin notice / disabled feature) — never a fatal that takes down the host. This is verified, not assumed.
- **Forge issues get a living log.** When work originates in — or resolves — an issue on the project's forge (GitHub, GitLab, Gitea, Bitbucket, any other), `docs/issues.md` (template and rules in `references/project-state.md`) is updated at the moment it happens: inventory on triage, and the issue's entry (diagnosis, resolution, commits, verification, pending) as the work is done. The slice that resolves an issue is not done until its entry is written — exactly like its docs and tests.

## Steps

### 0. Plan sprints and extend the tracking (before any code)

Real projects don't fit in one chat. Plan the work as sprints so it survives across sessions and a fresh chat can resume faithfully. The state files (`docs/PROGRESS.md`, `docs/decisions.md`, `docs/lessons-learned.md`) exist since Phase 1 (per `references/project-state.md`) — this step extends them with sprint tracking; it does not create them.

- **Confirm the technical plan.** Re-read `docs/03-technical-plan.md` with the user and complete anything still open (exact tooling commands, test framework specifics). From here on it is the build's rulebook: conventions, error handling, code map.
- **Define the sprints with the user.** Sprints are not fixed-size; decide them together based on this project (a sprint may be one slice or several, e.g. "OAuth + PKCE end to end"). Each sprint is a coherent, closeable chunk with its own acceptance.
- **Create one file per sprint:** `docs/sprints/sprint-<N>.md`, using the sprint template in `references/project-state.md` — scope, slices, acceptance, status.
- **Extend `docs/PROGRESS.md`:** record the sprint plan in the phase-status table and set "Current position" to sprint 1's first slice. During development PROGRESS.md always names the current sprint and the exact point within it. Update it continuously, not just at sprint end.
- **`docs/lessons-learned.md` keeps accumulating.** Whenever something is tried, fails, and a working solution is found, record the problem and the solution so the same mistake is never repeated. Append-only; never trim it.

**Do this step in plan mode when the environment offers one** (Claude Code's plan mode, Cursor's plan mode, Gemini CLI's plan approval mode, or an equivalent): explore the spec, the technical plan and the code map first, present the complete sprint plan for the user's approval, and only then touch anything. Where no plan mode exists, the same discipline holds — the sprint set is presented and approved before any code is written.

#### Sprint kickoff — repeat at the start of EVERY sprint, not only the first

1. **Enter plan mode again** (when the environment offers it) and lay out how THIS sprint will be built before building it: the slices in order, the files each touches (from the code map), the tests each will add (unit / integration / e2e per the coverage rule in §2), and the flow each exercises in the playground. The plan is presented to the user before any code — in plan mode where it exists, as the written plan in `docs/sprints/sprint-<N>.md` otherwise — and the approved version lands in that sprint file either way.
2. **Re-validate what you think you know — assumptions rot between sessions.** Verify against the source, never against memory, before planning on top of it: the current state of the code the sprint touches (read those files — do they still look like the plan assumes?), the platform and dependency versions (has WordPress/WooCommerce/the runtime/a pinned dependency released something since the plan was written? does the support matrix still hold?), and any external API, hook, or schema the sprint builds against (is it still what the spec recorded?). Anything that changed is a recorded plan/spec amendment, never a silent improvisation; anything uncertain is settled NOW with a file read, a command, or a doc lookup. A sprint built on a stale assumption is rework with extra steps.
3. **Confirm the playground still boots** from its documented commands (this is the same session-start freshness rule as §4 — at a sprint kickoff it is simply mandatory).

### 1. Scaffold

Create the project structure per the technical plan's code map, the `docs/` dir (already seeded by earlier phases), and a `tests/` location. Set up `.gitignore` and `.gitattributes` now (full rules in Phase 7) so secrets and build cruft never enter history from commit one.

**Generate and run `scripts/keel-doctor` FIRST — before gate zero, before any code.** Compile it from `docs/03-technical-plan.md` §Environment requirements (Phase 2 §4d) per `references/test-automation.md`: three modes (`--check` detects only and never needs privileges; `--plan` prints the exact commands it would run without running them; `--fix` runs them after the user's OK on the itemized list), a five-column table distinguishing `OK` / `TOO OLD` / `NOT OPERATIONAL` / `MISSING`, and a `--json` mode so the assistant reads structured output instead of parsing its own table. Commit it. Run `--check`; if anything blocking is missing, show `--plan` and ask once — the user sees the literal command list before a single thing is installed, and may decline any row. Nothing global is installed silently, no licence is accepted on the user's behalf, and anything that genuinely needs a human (a platform toolchain behind two-factor authentication, a system permission that cannot be scripted without weakening security) is reported as a clear stop rather than attempted. From here on `--check` runs at the first test point of every session and at the Phase 7 gate.

**Verify the toolchain end to end before slice 1 — gate zero:** run the exact lint / test / build commands from `docs/03-technical-plan.md` on the scaffold. Gate zero is a clean build/compile, a clean lint pass, AND one trivial passing test — all green before the first slice; no slice is written on a toolchain that has not proven it can catch anything. A broken toolchain discovered at slice 8 costs a day; discovered here it costs minutes. Record the verified commands back into the technical plan if they changed.

**Stand up the verification playground with the scaffold (whenever the project can be run):** create the environment from the recipe the technical plan chose out of `references/playground-recipes.md` — `docker-compose.yml`, wp-env config, a playground script, a disposable sandbox — including its synthetic seed-data fixture and its documented reset command (fixtures are synthetic only, never real customers/orders/emails: the confidential-data rule covers test data too), start it with the documented commands and verify the software actually loads in it. Create `docs/playground.md` now: exact start/stop commands, access details (URL/host, user, password — local, throwaway credentials only; never production secrets, never reused ones), and step-by-step try-it instructions per flow, extended as slices land. Those instructions exist so the user CAN look at the current state whenever they want — never so they have to test it on the assistant's behalf.

**Stand up the test drivers with the same scaffold, and prove each one actually drives something.** Install the driver named for every surface in the plan's "Driver per surface" table, and write one trivial driven test per surface that opens the thing, asserts one true fact, and produces its evidence artifact — a browser test that loads a page and asserts its heading, a protocol call that lists the server's tools, a UI test that launches the app and finds one element. This is gate zero for the drivers: a driver that has never driven anything is not installed, it is merely present. Configure headless operation up front, and where a platform makes that impossible apply the mitigation the plan recorded (a simulator created for this project rather than the user's own, a virtual display, a dedicated machine or user session) — the user's screen is never taken by surprise. Wire the read-back from this first test: console errors, uncaught exceptions, failed requests, 5xx responses and the platform's own log are collected and fail the test. Per `references/test-automation.md`.

**Build the debug-log system into the product at the scaffold — logs are how the user hands the assistant a debuggable failure.** Every runnable project ships a logging mechanism designed for copy-paste diagnosis: timestamped entries with context (component, action, relevant state — NEVER secrets, tokens, or real personal data: the confidential rule covers logs too), written where the user can reach them, with a simple switch to turn generation on and off:

- **WordPress / WooCommerce:** use the platform's own system — for Woo, `WC_Logger` (`wc_get_logger()` with the plugin slug as source; the user reads and copies it under WooCommerce → Status → Logs); for plain WP, a plugin-managed log surfaced in the admin. The switch is a checkbox on the plugin's settings page, with a constant/filter override.
- **PrestaShop:** `PrestaShopLogger` or a module log, with the checkbox in the module's configuration page.
- **Custom webs/apps with a control panel:** a toggle in the panel; without a panel, an env var or config constant.
- **MCP servers / CLIs / libraries:** an env var or constant; MCP servers log to stderr, never stdout (stdout corrupts the protocol stream).

The switch defaults ON through Phase 5 and OFF at release — Phase 7 verifies the shipped default. The logging code itself is never stripped once everything works: a production incident with a switchable log is diagnosable the same day; one without it is archaeology. `docs/playground.md` records where the log lives, how to flip the switch, and how the user copies entries to paste back to the assistant.

**Generate `scripts/keel-verify` with the scaffold** (see §1a below) and keep it current from here on: the checks exist before there is anything for them to catch, and every sprint close and the Phase 7 gate run the same executable instead of re-checking promises by eye.

**Create the front-end asset build at the scaffold (only if the project ships JS/CSS).** Generate the build/minify script named in the technical plan and wire the source→minified pairing from the first asset: every shipped file exists as `name.js` + `name.min.js` (and `name.css` + `name.min.css`) in the same directory, the unminified file is the source that gets edited, and the minified file is only ever produced by running the script. The working assistant runs it locally before committing — never a CI or forge action, which the project must not assume exists. A `.min.*` is never written or edited by hand. This is the SKILL.md "Build assets — source first, minified for production" contract; it holds unless the developer records a different pipeline in `docs/decisions.md`.

**Complete the assistant config package (if accepted at step 0a — per `references/assistant-config.md`):** propose the permission allow-lists with ONLY the technical plan's verified tooling and playground commands — one container per capable accepted tool (`.claude/settings.json`, `.codex/rules/`, `tools.allowed` in `.gemini/settings.json`, `.cursor/cli.json`) — and write them on the user's confirmation; install the confidential-data pre-commit gate (`.githooks/pre-commit` + `git config core.hooksPath .githooks`) and VERIFY it blocks a synthetic secret before slice 1; create the MCP registration only if the technical plan defines development MCP servers (per-tool containers, environment expansion, never a literal secret); and materialize the optional CI workflow from the plan's exact verified commands (per `references/assistant-config.md`) — CI runs the same lint / test / build the test points run, never a diverging set. Package or no package, the scaffold's `.gitignore` ALWAYS includes `CLAUDE.local.md`, `.claude/settings.local.json`, and `.keel-update-check` (the machine-local update-check throttle stamp) — plus the accepted tools' personal files per `references/assistant-config.md`.

**Commit discipline (from the first commit):** commit at minimum at every passed test point, with a message naming the slice; never end a working session with the repo in a broken state — if a slice is mid-flight, the exact stopping point goes in `docs/PROGRESS.md`. Git history is part of the project's resumable state. Every commit is preceded by the confidential-data check (SKILL.md "Confidential data never reaches Git"): scan the staged files for secrets, credentials, private keys, or real personal data; a finding stops the commit, is reported to the user as a security risk, and is excluded via `.gitignore` (untracked, or history-purged and rotated if it ever reached the remote) before anything is committed.

### 1a. `scripts/keel-verify` — the project's own release linter

The scaffold generates a small executable at `scripts/keel-verify`, and every later slice that adds a checkable promise keeps it current. Keep it dependency-light — plain shell or the project's own runtime, nothing the toolchain does not already have. Its job is mechanical: verify that what the docs promise is actually true, so no session re-checks it by eye and no release ships with a promise broken:

- **Version touchpoints in sync:** every place the version string lives per `docs/03-technical-plan.md` §Version touchpoints carries the same value.
- **Changelog order:** oldest → newest. An inverted changelog fails the run.
- **`docs/api/INDEX.md` parity:** every row's doc exists; every doc in `docs/api/` and `docs/reference/` has its row.
- **Documented extension points exist in the source.** Every hook, filter, action, event or callback name documented in `docs/api/` or `docs/reference/` is found in the source tree. A documented extension point that is never fired — or fired under a different name after a rename — is invisible from inside the project and produces the most expensive support ticket an extensible project gets: an integrator writes code against it, nothing runs, and the report arrives as "your plugin is broken" with no reproduction the maintainer can see (trap 5 in `references/anti-patterns.md`). The grep proves the name exists; the test named in the slice rules proves it fires with the documented arguments.
- **No placeholder copy in distributable surfaces:** readme, shipped user-facing docs, UI strings — a leftover TODO/lorem/placeholder marker fails the run.
- **WordPress projects:** a dry-run `wp i18n make-pot` (or the PHPCS i18n sniffs) — untranslated or wrongly-domained user-facing strings fail the run.
- **Minified-asset sync (projects that ship front-end JS/CSS):** every `*.min.*` matches a fresh minify of its committed source; a stale or hand-edited minified file fails the run.
- **Cited commands exist.** Every command named in `CLAUDE.md`, `AGENTS.md`, the README and `docs/` resolves to a real script, a real package/composer script, or a real CI step. A documented command that does not exist is the single most expensive documentation defect in a Keel project: the next assistant runs it, fails, and invents a workaround that nobody recorded (trap 2 in `references/anti-patterns.md`). The documentation cites the script; the script is the truth.
- **Internal doc links resolve, and no doc is orphaned.** Every relative link inside `docs/` and `guide/` points at a file that exists, and every document is reachable from `docs/PROGRESS.md`, `docs/api/INDEX.md` or another linked document. An orphan is not wrong, it is invisible — which is how the same question gets answered twice, differently (trap 12).
- **Code-map markers are honest.** Every path marked `[E]` in `docs/03-technical-plan.md` exists on disk. A marker that claims an artifact Keel never built is the target-tree-as-inventory trap (trap 4) with a check in front of it.
- **Code fences are balanced.** An unclosed fence silently swallows the rest of the document when rendered, so a doc that looks complete in the editor is truncated everywhere it is actually read.
- **Keel conformance is complete.** Every requirement of `MANIFEST.md` Table 1 carries a row in `docs/keel-conformance.md` with exactly one state. Fail if: a row is absent, its state is not one of the four values, a `present` row's path does not exist, a `declined` row cites no real `docs/decisions.md` entry, or an `n/a` row's condition text is not the manifest's own Condition text for that row. A requirement whose phase has not been reached yet is legitimately `missing` with its phase named — that is not a failure, it is the checklist doing its job; what fails is a requirement due at or before the current position that is `missing` with no decision. This is what makes "apply Keel" mechanical rather than a matter of anyone's memory (SKILL.md "Applying Keel completely").
- **Every acceptance criterion is covered, by ID.** Collect every `AC-nn` ID from `docs/02-functional-spec.md` §6 and every `Criterion`/`Coverage` pair from `docs/05-test-points.md`. Fail if: an `AC-nn` has no row; a row's `Coverage` is empty or is not exactly `driven` or one of the eight delegation tags; a tagged row has no steps. This is a grep over two ID sets and one enum — deliberately mechanical, because the coverage rule is worthless if the only thing enforcing it is the assistant's own account of itself (`references/test-automation.md`).
- **Interactive elements carry their test identifiers.** In UI projects, grep the source for the stack's interactive element patterns (the list is recorded in the technical plan's conventions, so this check is a fixed pattern set and not a judgment) and fail on any that lacks the project's addressability attribute. Where a stack makes this ungreppable, the check is dropped from the script and moved to the `code-reviewer` checklist, on the record — never left as a promise the script pretends to keep.
- **Suppression count did not grow.** Count the narrow suppressions in the codebase (`eslint-disable`, `phpcs:ignore`, `@SuppressWarnings`, `# noqa`, and the project's equivalents) and compare against the count recorded at the previous sprint close. Growth is not an automatic failure — it is a reported number that has to be justified at the sprint close. A count that climbs every sprint means a standard is not working and needs revisiting, not routing around.

Extend it whenever the technical plan adds a new mechanically checkable promise (a new version touchpoint, a new distributable surface, a new change-map row that can be checked). It runs at every sprint close (§5) and at the Phase 7 gate; wherever it runs, its output is pasted as evidence — "keel-verify passed" without the output is an empty cell.

**Every trap closed by prose alone is still open.** When a problem is found that could have been caught mechanically, adding the check to `keel-verify` is part of fixing it, not a follow-up task — this is the standing rule of `references/anti-patterns.md`, and it is what keeps the catalogue from becoming a list of things everyone agrees with and nobody enforces.

### 1b. Verification that cannot run yet is "not yet applicable" — never "passed"

Verification grows with the repository. In the first slices most of the gate does not exist yet: there is no full suite to run, no playground to boot, no release package to lint. Two rules govern that window, and both exist because the alternatives are a false green and a false red.

1. **Never use a later gate as a proxy for a missing earlier artifact**, and never the reverse. Run the checks whose inputs actually exist, at the scope they cover.
2. **When a check cannot run because its inputs do not exist, report it as "not yet applicable", naming the missing artifacts.** Not "passed" — that is a claim nobody made. Not "failed" — that is a defect nobody has. "Full suite: not yet applicable — no integration tests exist before slice 3" is a complete, honest, actionable report; it tells the reader exactly what would have to exist for the answer to change.

The same applies to the definition-of-done checklists reported at every phase close: an item whose evidence cannot exist yet is marked as such with the reason, never silently ticked. Claiming verification that did not happen is worse than reporting a failure — it converts a known problem into an unknown one, and it is the fastest way to lose the trust that makes working across sessions possible at all (trap 7 in `references/anti-patterns.md`).

### 1c. When the gate itself is wrong — the only escape hatch

A gate that fires on correct code destroys trust in every other gate, so there has to be a legitimate path — and it has to be narrow, or it becomes the path for everything. In order, no skipping:

1. **Fix the code.** The default assumption: the gate is right. Most of the time it is.
2. **Fix the gate**, if it is genuinely wrong — in its own commit, with the reason in the message, so the change is reviewable as a change to the standard rather than buried inside a feature.
3. **Suppress narrowly**: one line, one rule, with a comment stating why and a link to the record (`docs/decisions.md` or the issue). Never a file-level or project-level disable.
4. **Never** an override, a deleted test, a relaxed assertion, a lowered threshold, or a `--no-verify` commit. If that seems necessary, the gate is wrong and the answer is step 2.

Every step 2 and step 3 is recorded: a gate change is a D-entry in `docs/decisions.md`, and a suppression is counted by `keel-verify`. This is the ONLY sanctioned way around a red check — everything else is the "loosened to get green" trap (trap 8), which re-opens exactly the failure the check was written for and hides it behind a passing run.

### 2. Build in vertical slices with test points

Work feature/flow by feature/flow, not layer by layer. For each slice:

- **Confirm the slice's inputs before writing anything, and read its change-map row.** The code map is a target tree: check that every path this slice depends on is really marked `[E]` and really on disk, and stop if one is missing rather than building on top of an assumption (`references/phase-2-functional-spec.md` step 4). Then read the change map's row for this slice's type of change — it is the checklist of everything that must be touched, and it exists precisely so no slice has to re-derive it. If this slice is a type of change the map has no row for, add the row now, in this slice.
- **Search the existing internal API before writing new code.** Consult `docs/api/INDEX.md` first (one line per public surface — per `references/project-state.md`); open the full doc in `docs/api/` or `docs/reference/` only on a hit. Reuse if it exists. If a near-fit exists, generalize the existing function instead of forking it. Only create a new function when there is genuinely no fit. Record any reuse/generalization in the slice's notes.
- Implement the slice to its functional requirements.
- **Add extension points as you go (extensible project types).** For WordPress/WooCommerce plugins, MCP servers, and libraries: as each user-facing string, decision, query, and response is written, expose the corresponding filter/action (or platform-equivalent extension point) with the project's prefix. Default to "filterable" rather than hard-coded; opt out only with a recorded reason.
- **Document this slice's public-surface changes — all three kinds, now, not later.** Per SKILL.md "Document every public surface at the moment it changes", every surface this slice **creates, modifies, or removes** is reflected in `docs/api/` and/or `docs/reference/` and in `docs/api/INDEX.md` within the slice itself:
  - **Created** — write the entry (signature, params, return, errors, auth, runnable example) AND its one-line INDEX row. The example must actually run.
  - **Modified** — update the existing entry to the as-built reality: signature, parameters, return values, errors, permissions, behavior, and the example, re-run so it still works. Also update its INDEX row if the purpose or the code file changed. Changing a surface and leaving its doc untouched is a slice defect: the doc now lies, and nothing downstream will catch it.
  - **Removed** — never delete silently. Never released: delete the entry and its INDEX row in this slice. Already released: keep the entry, mark it deprecated/removed with the version and the replacement, update its INDEX row, and append the D-entry in `docs/decisions.md` (removing a released surface is a gated breaking change — see "Migrations and backward compatibility" above).

  Also update anything else that referenced the surface: other docs' examples, the technical plan's code map, and `docs/architecture.md` if it exists. An INDEX row without its doc, a doc without its row, and a doc describing a signature the code no longer has are all slice defects.
- **Comment the code as you write it.** Every public surface introduced by the slice gets its docblock in the platform's convention (purpose, params, return) at the moment it is written, and every non-obvious decision gets a why comment — never backfilled later. Comment language follows the recorded policy (English by default). `code-reviewer` flags gaps as slice defects.
- **Build the slice accessible as you write it (UI slices).** Use semantic/native controls first; expose accessible name/role/state to the platform accessibility API; ensure keyboard/assistive-tech operability, visible focus and correct focus order; meet contrast and target size; identify errors non-visually too; honor reduced motion, text scaling and high contrast. If there was a design handoff, implement to `SPEC/accessibility.md` / `BUILD-SPEC.md` §4a. Per `references/accessibility.md`.
- **Regenerate minified assets from source (asset slices).** If the slice touched a front-end source asset, regenerate its `*.min.*` by running the project's build/minify script before the commit — never by hand-editing the minified file. Source and minified stay a matched pair; a stale or hand-edited minified file is a slice defect. Per SKILL.md "Build assets — source first, minified for production".
- **Every acceptance criterion gets a named automated test, and the assistant drives it.** Each acceptance criterion from Phase 2 §6 that this slice implements maps to a named automated test wherever the platform can express it — unit for logic, integration where components meet, end-to-end for user-visible flows (for web UI, a browser-driven e2e when the environment can run one — per the recipe in `references/playground-recipes.md`). For anything user-visible that means the test **fills the real fields** — valid, empty and invalid — clicks the real controls, waits on real state, and asserts what the interface actually shows, including the validation message, the empty state and the permission denial. Writing "the user will check that the error appears" instead of a test that enters the bad value and asserts the error is a slice defect, not a shortcut (`references/test-automation.md`). Every new interactive element carries its stable test identifier in the same slice — never a faked accessibility label, which is read aloud to real users. A criterion left without a driven test carries one of the eight delegation tags from `references/test-automation.md` in the `Coverage` column of `docs/05-test-points.md`, with the steps for whoever will run it. **There is no free-text exemption:** "not worth automating in this slice" is not a tag, and a row whose coverage is prose rather than one of the enum values fails `scripts/keel-verify`. The exception lives on the record as a tag, or it does not exist. Where Phase 2 recorded a **reference test suite** as the spec for a feature (Reference artifacts), that suite is the acceptance contract for everything it covers: run it as delivered rather than re-deriving a parallel set of tests from the prose, which only creates two specs that can disagree. The exception is always the cases its entry marked as deliberately changed: those are re-expressed as new named tests, the delivered case is removed or overridden, and the divergence is recorded in `docs/05-test-points.md`. **Where the suite and the spec disagree anywhere else, the spec governs** and the conflict is raised, never resolved by making the old test pass.
- **Test point:** verify the slice against its acceptance criteria from `docs/02-functional-spec.md` — success path, empty, invalid, permission failure, and the failure/recovery branch from its flow file. Write automated tests where the output is objectively verifiable; for UI, verify against `docs/BUILD-SPEC.md` state matrix. If a playground exists, also exercise the slice in it for real — walk its flow end to end, run its CLI command, call its endpoint — not only through the automated suite, and extend `docs/playground.md` if the slice added something tryable. The test point also confirms: (a) no duplicated function was introduced; (b) every public-surface change in the slice is reflected in the docs — created surfaces documented, modified surfaces updated (signature, params, return, errors, permissions, example), removed surfaces resolved per the removal rule — and every example the slice touched was re-run and works; (c) for extensible types, the planned extension points are present and prefixed; (d) for UI slices, accessibility is verified — the automated check AND the driven keyboard/focus-order pass, both run by the assistant, against `references/accessibility.md` and the accessibility spec; the real assistive-technology pass is `ASSISTIVE-TECH` and is batched at the sprint close per flow rather than demanded of the user slice by slice (it is repeated when a flow's accessibility-tree snapshot changes, not on every commit); (e) if a playground exists, the slice was exercised in it for real BY THE ASSISTANT — driven, not described — with the console/network/log read-back clean and the static analysers and sniffers run with their output recorded; any leg that could not be driven carries one of the eight delegation tags (`references/test-automation.md`) plus the exact steps, and stands as `⚠ unverified` until someone runs it — a delegation with no tag is a defect; (f) independent review — when the environment provides subagents (or the project carries assistant subagents per `references/assistant-config.md`), the slice diff was reviewed by `code-reviewer` before its commit, and the slice's driven verification ran through `test-driver` (the cheap mechanical role — it executes the tests and reports, it does not author criteria), with every finding fixed or explicitly recorded; where the environment has no subagents, the same work runs inline and that is recorded rather than skipped; (g) the slice's change-map row was satisfied item by item — every artifact the row names was touched, or its absence has a stated reason — and any `[A]`/`[G]` path this slice made real is now marked `[E]` in the code map, in this same commit; (h) if the slice added, changed or removed a control named in `docs/threat-model.md`, that row's delivery state was updated (`TO BUILD` → `IN PLACE` only with the evidence), and any protection deliberately not built went into the "Not defended" table with its consequence rather than staying silent.
- **Record the evidence, not the claim.** Every test-point row in `docs/05-test-points.md` records the exact command(s) run, a result summary (n tests, 0 failures; build OK; playground boot OK), and the commit hash. A result without its command and output is an empty cell — and an empty cell is a missing check.
- Run the relevant security checks from the profile for this slice (e.g. nonce/capability for a WP admin action, scope/PKCE for an OAuth step, input sanitization, output escaping).
- **If the slice fixed a bug, pin it with a regression test** in the same slice, and link the test from the `docs/lessons-learned.md` entry. If the bug (or feature) came from a forge issue, update its `docs/issues.md` entry in the same slice: diagnosis, resolution, commits, verification, anything pending.
- **After 3 failed attempts at the same test point, STOP.** Record the problem and the failed attempts in `docs/lessons-learned.md` — a provisional entry with no solution yet is itself information — and report to the user with options: provide context the assistant lacks, change the approach, or park the slice with its exact position noted in `docs/PROGRESS.md`. Never loop past three attempts without the user, and never "fix" the failure by deleting, skipping, or loosening the test (see Principles).
- Only move to the next slice when this one passes its test point. **Commit the passing slice** (message naming the slice) and update `docs/PROGRESS.md` and `docs/05-test-points.md` before continuing. Report the test-point result to the user on substantial slices.

### 3. Integration test points

After integrating external services: verify auth, the happy path, rate/quota handling, and failure handling against the spec. Never hardcode secrets — load from environment/secure store per the security profile.

### 4. Cross-cutting verification

Before declaring development done, run the full pass: all acceptance criteria, all flows including failure paths, the full security profile checklist, and (if UI) the Phase 4 faithfulness checklist still holds after wiring. If a playground exists: run the full pass in it too — every flow exercised for real (UI walked, CLI commands run, API called) — verify `docs/playground.md` matches reality (start/stop commands, access details, try-it instructions), and invite the user to try the flows themselves with those instructions. If UI: accessibility verified end to end against `references/accessibility.md` — automated checks plus keyboard-only and real assistive-technology passes, at the largest text size, with user preferences honored. If multi-language: confirm no user-facing string is hardcoded or concatenated, every string uses the translation mechanism with the right text domain, and the base locale file is generated and current. Verify every declared performance budget (`docs/03-technical-plan.md` §Support matrix & budgets) with the measurement method the plan named, recording the numbers — a budget without its measured number is unverified. Run `scripts/keel-verify` and paste its output into `docs/05-test-points.md`.

**Session-start freshness (every working session, not only this step):** at the FIRST test point of each session, boot the playground from the commands documented in `docs/playground.md` exactly as written — this validates the environment and the document in one move — and stamp `last verified: <date>` in `docs/playground.md`. Instructions that no longer start the playground are a defect caught now, not by the user.

### 5. Close the sprint (mandatory at the end of every sprint)

When a sprint's scope is complete and its test points pass, run this close-out before starting the next sprint. Do not skip it — this is what makes the project survive across chats.

1. **Leave the repo clean:** the FULL automated suite green — every test in the project, not only this sprint's: a sprint-3 regression over sprint-1 code must have a detection point — and everything committed. Run `scripts/keel-verify` and paste its output into the sprint's file, and record the sprint's **suppression count** there so the next close has something to compare against. A sprint never closes with a broken, failing, or uncommitted state.
2. **`docs-verifier` at close (when the environment provides subagents — per `references/assistant-config.md`):** run it over everything the sprint touched — every INDEX row has its doc, every doc has its row, examples reference symbols that exist. Findings are slice defects: fixed before the close, never carried.
3. **Playground-QA pass — a fresh-context check:** a checker with no memory of this sprint — the `playground-qa` subagent when the environment provides one, a clean session otherwise — receives ONLY `docs/playground.md` and follows it literally: start the playground from the documented commands, walk every try-it flow, report where it breaks. It proves the document, not the assistant's recollection. Wherever it breaks, something is defective — the software or the instructions — and it is fixed before the sprint closes; an instruction gap is a defect like any other.
4. **Report the sprint to the user with evidence — and ask them only for what they alone can answer.** By this point the assistant has already driven every flow the sprint implemented: filled the fields, walked the branches, read back the logs. So the hand-over is a *result*, not a homework assignment. Give the user:

   - **What was verified and how** — one line per flow with its evidence (the recording, the screenshots, the trace, the result bundle), so they can see the product working without operating it.
   - **What could not be driven**, each with its tag and its steps: the `CREDENTIAL` legs needing their sandbox keys, the `ASSISTIVE-TECH` guided pass, the `HARDWARE` cases. This is the only list the user is asked to act on, it is as short as the platform allows, and it never contains anything the assistant could have automated.
   - **What needs their judgment** (`JUDGMENT`): wording, behaviour that is technically correct but may not be what they meant, a trade-off they should know about. This is a product conversation, not a test.
   - **Where the debug log is and how to copy it**, so that IF they do try something and it misbehaves, the report comes back with the log attached and the diagnosis takes one round trip instead of twenty questions.

   Trying the build themselves stays available and welcome — `docs/playground.md` has the access details and the steps, and some people simply want to click around their own product. It is an invitation, never a duty. **A sprint close that hands the user a numbered list of screens to visit and messages to confirm is a defect in this phase**: those steps were the assistant's job, and every one of them should already be a driven test with its evidence attached. Record the verdict in the sprint's close-out; a reported failure reopens the sprint (fix + its regression test, and the missing driven test that would have caught it) before anything new starts.
5. **Update `docs/PROGRESS.md`:** mark the sprint's tasks done, record what was completed, and state exactly what the next sprint is and what remains. PROGRESS.md must always reflect reality. Close the sprint's file (`docs/sprints/sprint-<N>.md` status + close-out). Append the sprint's working sessions to `docs/token-ledger.md` if any row is missing (per `references/estimation-budget.md`).
6. **Update `docs/lessons-learned.md`:** add every lesson discovered during the sprint in the symptom → cause → fix shape, including its **"Check added"** field — a lesson that could have been caught mechanically is not closed until that check exists in `scripts/keel-verify` or the test suite. If nothing failed, note that explicitly so it's clear it wasn't skipped. For each lesson, decide its destination: specific to this project, it stays here; a trap that would bite ANY project of this class, propose codifying it into Keel's `references/anti-patterns.md` (per SKILL.md, an agreed improvement is codified into the skill, not only into the project that found it). If forge issues were worked this sprint, verify `docs/issues.md` reflects them: entries complete, inventory current.
7. **Run the self-audit from `references/anti-patterns.md`** — every answer from a command or an artifact, never from recollection — and record the answers in the sprint's close-out. This is the sprint-level counterpart of the Phase 7 gate's run: catching a drifted doc, a dead command, an unmarked code-map row or an unwired generator at a sprint close costs minutes; catching it at the release costs the release. A failing answer is fixed before the sprint closes, or it becomes a recorded open item in `docs/PROGRESS.md` with the reason — never silently carried.
8. **Archive what's no longer needed:** move documents that are finished AND no longer consulted from `docs/` into `docs/old/sprint-<N>/` (move, never delete — they stay traceable). Follow the archiving rules in `references/project-state.md`: the state files, specs, technical plan, flows, design handoff, api/reference docs, and the current sprint file NEVER move while the project is alive.
9. **Generate the continuation prompt** using the universal template in `references/project-state.md`, with the sprint specifics added: the next sprint's file (`docs/sprints/sprint-<N+1>.md`), the instruction to build **faithfully to the existing spec and design — no reinterpreting, no deviating, no inventing** (gaps go to a Design Request, exactly as in Phase 4), and to run the same per-slice test points and close the next sprint the same way. It MUST be self-sufficient — a new chat has no memory of this conversation or the design.

   **Show the prompt to the user directly, unprompted, as part of the close** — with the one-line instruction to paste it into a NEW chat to continue the development. The user never has to ask for it. If the current chat still has capacity, development may continue here — the prompt is insurance, not an order to switch chats.

## Test point log

Maintain `docs/05-test-points.md`:

```
# Test Points — [Project name]
| Slice | Criterion (AC-nn) | Coverage (`driven` or a delegation tag) | Delegation steps (when tagged) | Real run in playground | Security checks | Accessibility (automated + AT pass) | i18n (strings externalized) | Reuse checked (no new duplicate) | Docs updated (api/reference, example runs) | Extension points exposed (filter/action) | Evidence (commands + output summary + commit) | Result | Notes |
```

Every slice must appear with a result before Phase 6. The playground, accessibility, reuse, docs, extension-point, and evidence columns are not optional fields — an empty cell is a missing check. The evidence cell carries the exact command(s) run, a one-line result summary, and the commit hash — a result without them is an empty cell.

**`Criterion` and `Coverage` are the two columns `scripts/keel-verify` reads, so their format is fixed, not free.** `Criterion` holds the acceptance criterion's stable `AC-nn` ID from `docs/02-functional-spec.md` §6 (or `—` for a check that is not criterion-bound). `Coverage` holds exactly one of: `driven` — a test drove it, and the command plus its evidence are in this row — or one of the eight delegation tags from `references/test-automation.md` (`CREDENTIAL`, `HARDWARE`, `ASSISTIVE-TECH`, `JUDGMENT`, `EXTERNAL-APPROVAL`, `PLATFORM-IMPOSSIBLE`, `PRODUCTION-RISK`, `NO-EXECUTION`), in which case the next column carries the exact steps for whoever will run it and the result stays `⚠ unverified` until they report back. Prose in the `Coverage` column is a defect: the whole point of the enum is that a script can count the rows that are neither. (The accessibility cell applies to UI slices; the playground cell to runnable slices; where genuinely not applicable record "n/a".)

## Definition of done

- Every v1 feature implemented to spec with its test point passed and logged.
- Every flow, including failure/recovery paths, verified.
- **Every acceptance criterion has its named automated test** (unit / integration / e2e per its nature) or its one-line recorded justification in `docs/05-test-points.md` — no criterion untested implicitly.
- **The FULL automated suite is green and `scripts/keel-verify` runs clean**, its output pasted as evidence.
- **`scripts/keel-doctor` exists, is committed, and `--check` passes** — generated from the technical plan's environment requirements, run before gate zero and at the first test point of every session.
- **The assistant drove everything it could drive.** Every user-visible acceptance criterion has a driven test that fills the real fields (valid, empty, invalid) and asserts what the interface shows; console errors, uncaught exceptions, failed requests, 5xx responses and the platform log are read back and fail their tests; static analysers and sniffers ran at every test point with recorded output and a tracked suppression count. Every leg handed to the user carries one of the eight tags with its steps, and anything unrun is `⚠ unverified` — never silently absent, never reported as passing. No sprint close asked the user to walk screens the assistant could have driven.
- **Evidence complete:** every test-point row carries its exact commands, result summary, and commit hash — no empty cells.
- **Independent review happened** — `code-reviewer` on each slice diff, `docs-verifier` and the playground-QA pass at each sprint close — or the environment's lack of subagents is recorded; never silently skipped.
- **If the project can be run: the verification playground exists and starts from its documented commands.** Every flow, CLI command, and API surface was exercised in it for real — not only through the automated suite — and `docs/playground.md` is current: start/stop commands, access details (local, throwaway credentials only), and step-by-step try-it instructions the user can follow to verify the result themselves.
- **Every sprint was kicked off with an approved plan (plan mode where the environment offers it) and a source-checked re-validation of assumptions**, and closed with the assistant's driven verification report and its evidence — plus the user's answer on the tagged list of legs only they could run, where any existed. A sprint is NOT closed by asking the user to walk its flows and report back; that is the defect this phase now names explicitly (§5 step 4).
- **The product's debug-log system exists with its on/off switch** — platform-native where one exists (`WC_Logger` for Woo, a settings checkbox in WP/PrestaShop/panel apps, env var or constant elsewhere, stderr for MCP servers) — and `docs/playground.md` documents where the log lives and how the user copies it.
- Security profile checklist passed for every relevant boundary.
- **Accessibility built into every UI slice and verified** — automated and driven keyboard/focus passes by the assistant on every UI slice, real assistive-technology passes batched per flow at sprint closes under `ASSISTIVE-TECH` — meeting the Phase 1 targeted level per `references/accessibility.md`, with user preferences honored; if there was UI, built to `SPEC/accessibility.md`.
- **Internal API coherent and reused.** No near-duplicate functions/methods/classes; reuse verified per slice; the codebase has one canonical implementation per behavior.
- **Every public surface introduced in Phase 5 is already documented** in `docs/api/` and/or `docs/reference/` with a runnable example, **and has its row in `docs/api/INDEX.md`** — and every surface Phase 5 *changed* or *removed* was resolved in its own slice, so no entry describes a signature the code no longer has or a surface it no longer contains. Phase 6 will only consolidate — no undocumented and no stale public surface enters Phase 6.
- The build followed `docs/03-technical-plan.md` (conventions, error handling, code map current); any change to the plan was recorded as a decision, never silent.
- Every fixed bug has its regression test; every passed test point has its commit; the repo is clean and green.
- If the assistant config package was accepted: the permission allow-lists confirmed with the user (every capable accepted tool), the pre-commit gate installed and verified against a synthetic secret, MCP registration present only if the plan defines dev MCP servers (per `references/assistant-config.md`).
- If forge issues were worked: `docs/issues.md` is current — every worked issue has its complete entry (diagnosis, resolution, commits, verification, pending) and the inventory matches the forge.
- `docs/token-ledger.md` has a row per working session (measured or honestly estimated, method stated — per `references/estimation-budget.md`).
- **For extensible project types (WP/Woo plugins, MCP servers, libraries):** every meaningful user-facing string passes through a filter, every meaningful decision exposes an action before/after, every query/response is filterable, and every public class supports a documented replace/extend mechanism. All extension points are prefixed and documented in `docs/reference/hooks-and-extension-points.md` with at least one runnable example each.
- If multi-language: zero hardcoded/concatenated user-facing strings; every string externalized via the platform's idiomatic i18n mechanism (function-wrapping or key/constant catalog); base language is the Phase 1 base language (English by default — always English for WordPress/WooCommerce); base catalog/locale resource generated from it and current. WordPress/WooCommerce projects are verified multi-language-ready with an English `.pot` regardless of what the conversation language was.
- If installed base: upgrade tested from the real previous version (not just clean install); existing data preserved/migrated; backward compat held or breaking change gated and documented; clean uninstall verified.
- Every Phase 1 dependency: version checked and fail-safe behavior verified when absent/incompatible (no fatal).
- If UI: build still matches `docs/BUILD-SPEC.md`.
- `docs/05-test-points.md` complete (all columns, including accessibility / reuse / docs / extension points / evidence).
- Every sprint was closed properly: `docs/PROGRESS.md` reflects reality, `docs/lessons-learned.md` updated, finished docs archived to `docs/old/sprint-<N>/`, and a self-sufficient continuation prompt was produced at each sprint close.

No silent divergence from the spec or the design. Then Phase 6.

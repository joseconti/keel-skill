# Changelog — Keel

All notable changes to the Keel skill are documented here.
Versions are listed oldest → newest (never inverted). Format groups: Added / Changed / Fixed.

## 1.0.0

Initial public release (GPL-3.0-or-later).

### Added
- Full idea-to-release multi-phase workflow with on-demand phase reference loading (progressive disclosure).
- Phase 1 Discovery: honest idea assessment (no default praise), project type fixing, installed-base/upgrade reality, fixed-version external dependencies, blocking multi-language vs single-language decision (function-wrapping and key/constant i18n models, base language as source of truth), project-website intent capture, design-needed decision.
- Phase 2 Functional Spec: flows, data model, integrations, permissions, design split (including external manual setup and assets Design can't produce), acceptance criteria.
- Phase 3 Design Handoff: brief enforcing build-once-reuse-by-manifest, ask-don't-invent, exact tokens, `external-setup.md` and `external-assets.md`, the shared handoff contract.
- Phase 4 Faithful Build: audit-first, consolidated BUILD-SPEC, zero-deviation build, one-step-at-a-time guided external setup, one-asset-at-a-time guided generation of images Design couldn't produce (adapting Design's base prompt to the user's chosen generator), two-branch failure handling, Design Request mechanism.
- Phase 5 Development: sprint planning, `docs/PROGRESS.md` living tracker, `docs/lessons-learned.md`, vertical slices with test points, live security profile, i18n build rule, migrations/backward-compat for installed base, fail-safe external dependencies, mandatory sprint close-out with archival to `docs/old/sprint-<N>/` and a self-sufficient continuation prompt for a fresh chat.
- Phase 6 Documentation: full `docs/` layout (architecture, API, usage, reference, security) with runnable examples; changelog ordering rule (oldest → newest).
- Phase 7 Release: `.gitignore` vs `.gitattributes` export-ignore boundaries, versioning, real-environment verification hard gate, release artifacts.
- Phase 8 Project Website (conditional): study the product → `docs/design/PRODUCT-BRIEF.md`; honest "is a site warranted?"; site type and the site's own blocking language decision; section catalogue & sitemap; dedicated-domain vs subdomain decision tree; design direction; vanilla-by-default (no frameworks/libraries/CDN unless a user-approved static-site-generator exception); self-hosted fonts with a guided procurement loop; product screenshots (Design reserves the slot, guided capture, build fits the CSS); technical SEO and AEO; real-environment launch checklist. Reuses Phases 3–7 rather than duplicating them.
- Per-platform security profiles: WordPress/WooCommerce, web app, MCP server, library/component.
- Shared templates: handoff contract, design brief, build spec, design request.
- Version reporting instruction and GPL-3.0-or-later licensing.

Inline-in-HTML rule, absolute URLs, consistency with rendered content.
  - Self-hosted fonts: `font-display: swap` and shipping only the actually-used weights/styles.
  - Compression, cache headers, HTTP/2 or HTTP/3, and resource hints (`preconnect`, `preload`) added as SEO-relevant transport items.
- Phase 8 Launch Checklist updated to fetch and verify every well-known file on the live domain, validate JSON-LD on live URLs, confirm the AI-crawler policy on `robots.txt`, and check self-hosted fonts in the network panel.
- Phase 8 Section Catalogue: site-wide deliverables (the well-known set) listed alongside page sections so they enter sitemap planning instead of being treated as launch-time extras.
- Three cross-cutting operating principles in SKILL.md:
  - **Reuse internal API; never duplicate code.** Search the existing API before writing new functions; generalize close fits instead of forking; duplication is a defect.
  - **Document every public surface at the moment it is created.** Each new function/method/class/hook/action/filter/REST route/MCP ability/CLI command is documented in `docs/api/` or `docs/reference/` as part of the same slice that introduces it; Phase 6 consolidates instead of writing from zero.
  - **Maximum extensibility for extensible project types** (WordPress/WooCommerce plugins, MCP servers, libraries/components): every user-facing string filterable, every meaningful decision exposes before/after actions, every query and response filterable, every public class replaceable. Decided at spec time, built into each slice.
- Phase 5 Development reflects the three principles operationally: per-slice checklist now includes search-before-writing, docs-at-creation, and extension-points-as-you-go; `docs/05-test-points.md` columns extended to record each; Definition of done enforces all three.
- Phase 6 Documentation rewritten as consolidation rather than creation. Undocumented public surfaces or missing extension points entering Phase 6 are Phase 5 defects to fix, not Phase 6 work.
- Phase 1 Discovery: new Step 0 — **Competitive scan**.
  - Always asks the user upfront which competitors they already know about.
  - Produces `docs/00-competitive-landscape.md` with per-competitor inventory (functionalities + license/pricing + status + cited sources), unified deduplicated feature list (de facto baseline for the category), and external-demand list (real user requests with citable sources).
  - Feeds `docs/01-discovery.md` with a "Competitive landscape & opportunity" section: table-stakes features, differentiator candidates, and optional AI/MCP/agentic layer proposals labelled as added-value or forced-filler (forced-filler dropped, not softened).
  - Cannot-research handling: when the environment lacks web/search, the assistant says so plainly with the specific reason and offers three options — move to a capable environment (preferred), use a different agent and bring findings back, or skip with an explicit warning block recorded verbatim in the discovery doc.
  - Definition of done updated; Phase 1 cannot complete without the scan being done or its absence explicitly recorded with the warning.

### Changed

- SKILL.md phase map: Phase 1 description updated to "Competitive scan first, then idea, feature discussion, project type, constraints".

## 1.5.0

### Added
- **Output language & internationalization contract (English by default, always).** New cross-cutting section in SKILL.md plus two operating principles: the base/output language of everything built (source strings, UI copy, identifiers, commit messages) defaults to **English** in every project, never Spanish. At the start of every project the i18n questions are asked explicitly (multi- vs single-language, which output locales, is English the base). WordPress/WooCommerce is a fixed rule — base language always English and always built multi-language-ready — never Spanish-base. The docs language stays the user's working language (normally Spanish), a separate decision.
  - Phase 1 Discovery Step 6 rewritten from "internationalization decision" to "internationalization & output language", with the three explicit questions, the WordPress/WooCommerce fixed rule, the English-by-default base, and the discovery-doc template + definition of done updated.

- **Writing quality — perfect orthography (unbreakable).** New cross-cutting section in SKILL.md plus an operating principle: everything written, in any language and on any surface, must be orthographically and grammatically perfect. Spanish specifically must carry every accent/tilde, every ñ and the opening ¿/¡, with zero spelling or grammatical errors — treated like a code bug, never shipped.
- **Design assets are delivered build-ready — the build never transforms them.** New rule across the handoff chain: every logo and icon ships in **both SVG and PNG** (PNG at intrinsic size plus the platform's required densities/sizes), and every asset is delivered in a format the target build uses directly, so Code never has to convert, resize, recolor, rasterize, or re-export. An asset that would force a build-side transformation is an incomplete handoff (a Design Request).
  - `handoff-contract.md` rule 4 expanded; folder-structure note and "what complete means" updated.
  - Phase 3: new core principles (build-ready assets; every screen defined by what it DOES, not just how it looks), brief requirements and definition of done updated.
  - Phase 4: Step 1 reframed as the completeness gate run FIRST (verify Design delivered everything without exception; anything missing becomes a registered Design Request, never a build-side workaround); asset-format audit check added; faithfulness verification extended.
  - `design-brief-template.md`: logo in SVG+PNG, icons in SVG+PNG, build-ready formats requirement, per-screen "what it does", definition of done updated.
  - `build-spec-template.md`: asset map gains SVG+PNG and build-ready columns; faithfulness checklist gains design-system fidelity and asset-format items.
  - `design-request-template.md`: assets category covers missing formats (SVG/PNG) and non-directly-usable formats.
- **Complete skill copy (portability lock).** `project-state.md` embedded-skill rules hardened: copy the whole skill (every file), verify against the source manifest, retry on any gap, verify again, and if it still fails STOP and tell the user exactly which files did not arrive so they can move them — never leave a half-copied skill as if it worked. ## 1.6.0

### Added
- **Token economy — everything Keel creates defaults to English (READ FIRST).** New section at the very top of SKILL.md: every artifact Keel creates — the whole `docs/` set (discovery, specs, progress, decisions, lessons learned, architecture, API reference, playground instructions), continuation prompts for new chats, prompts and briefs handed to Claude Code or Claude Design, template instances, reports, commit messages, code comments — is written in **English by default**, because English is the most token-efficient language for an LLM and the living state is re-read in every session, so the saving compounds for the life of the project. The default is announced to the user in one line at the start of every project (and adoption); any other language is available on request, with the increased token consumption — and therefore cost — made explicit and the choice recorded in the project card and `decisions.md`. On resume/adoption of a project whose docs already exist in another language, the user is asked once whether to translate everything to English; the answer is recorded and never re-asked. The policy does not change the conversation language (the assistant keeps talking in whatever language the user writes) and never drops the product's shipping locales.

- SKILL.md: the output-language operating principle and the "Output language & internationalization" contract no longer default the docs to the user's working language — docs and every other created artifact default to English (token economy); the Phase 1 §6 question batch gains question 4 (docs language — confirm English or record an explicit off-English choice with the trade-off acknowledged).

- `adoption.md`: the docs-language question now states the English default and includes the one-time offer to translate existing non-English docs to English.

## 1.7.0

### Added
- **Estimation & budget — AI-time based.** New cross-cutting reference `references/estimation-budget.md`: when the user needs to quote a project (or a feature) to a client, Keel produces a realistic, itemized estimate and a client-ready budget computed from how the work is actually delivered — the **AI's working hours** (session wall-clock per phase, scaled by the recorded scope) plus the **vibe coder's supervision hours** (answering question batches, making decisions, real-world testing the AI cannot do, external setup, uploading code, client bridge) — **never from traditional human development time**. Itemized lines are mandatory (segment | what is done | hours; totals derived from the lines; visible contingency, +20–30% default).
  - Two fixed moments: **preliminary estimate at Phase 1 close** (wide ranges, so the user can answer the client early) and **firm estimate + client budget at Phase 2 close**; recomputed as a new, re-approved version on any recorded scope change; also runnable on adopted-project work.
  - Batched runtime questions: hourly rate + currency, AI access mode (subscription ≈ 0 marginal cost vs API pay-per-token) and model(s), contingency, the budget's language (a client-facing deliverable, asked per project — the internal estimate stays English per the token economy), taxes note, availability for the calendar estimate.
  - AI cost per model: token estimate by project size with the input/output split and the prompt-caching effect; **prices always verified online before quoting** (dated fallback table included, verified July 2026); on subscription the default recommendation is not to bill the AI as a line item, since it is not an extra expense.
  - Artifacts: `docs/estimate.md` (internal, English, versioned preliminary → firm) and `docs/budget.md` (client's language, developer block and AI block SEPARATE, priced line by line, totals, estimated calendar delivery, terms), plus a mandatory **present → adjust → approve** loop with the user, recorded in `docs/decisions.md`.
  - SKILL.md: new operating principle ("Budgets are AI-time based, never human-time based") and a cross-cutting "Estimation & budget" section; Phase 1 gains step 10 and Phase 2 gains step 7, with their doc templates and definitions of done extended; the PROGRESS.md phase-table artifacts include estimate and budget.
- **Token ledger (`docs/token-ledger.md`).** Actual token usage recorded as the project runs: one row per working session (date, phase/sprint, model(s), input/output tokens, method — measured via environment counters/API usage/provider dashboard, or honestly estimated from volume when nothing is exposed; the method is always stated). ## 4.0.0

Major release: **documentation and reality stop drifting by discipline and start drifting by failing a check.** Keel already demanded evidence over assertion; this version attacks the failure class that survives that demand — a doc, a map, a manifest or a security claim that quietly stops matching the code while both keep looking healthy. The response is never "write it more clearly": prose asks for discipline once per reader, a check enforces itself forever. So the code map now says which of its paths actually exist, every project carries the checklist of what each type of change must touch, the known traps of its class are read before starting instead of rediscovered, deliberate omissions are recorded rather than silent, and six new mechanical checks catch the rest.

### Added

- **`references/anti-patterns.md`** — the known-traps catalogue, loaded at Phase 1 the moment the project type is fixed, alongside the security profile and the accessibility reference. Twenty-three entries in the shape *the trap / why it happens / what it costs / the rule that closes it*: twelve universal (declared tools that never run, documentation contradicting the build, a fact pinned in five places, the target tree read as an inventory, the extension point nobody can reach, the generated artifact nobody consumes, verification claimed but not run, the gate loosened to get green, the silent omission, the control claimed but not shipped, two copies of one source of truth, the orphan document) plus sections for WordPress/WooCommerce, MCP servers, and web apps/websites/libraries. Every rule names a mechanical check wherever one is possible, because **a trap whose rule is only prose is a trap that is still open**. It closes with an eighteen-question self-audit where every answer must come from a command or an artifact, never from recollection — run at sprint closes, at the Phase 7 gate and at adoption, and the source of new `scripts/keel-verify` checks. It is the counterpart of `docs/lessons-learned.md`, not a replacement: lessons-learned is memory (what bit THIS project), anti-patterns is prevention (what has bitten this class of project before it started), and `references/project-state.md` now states which destination a finding goes to.
- **Code-map state markers `[E]` / `[A]` / `[G]` (`references/phase-2-functional-spec.md` §4).** Every row of the code map declares whether the path exists now, is to be created by the assistant in a named slice, or is generated by a tool once its source exists. The binding rule: **a path not marked `[E]` is absent until a slice creates it**, and no session may claim a path exists — or report work as in place — because the map shows it. Markers move in the commit that changes reality, exactly like the docs, and `keel-verify` checks that every `[E]` is really on disk. A tree diagram and a directory listing look identical on the page; this is what tells them apart.
- **The change map (`references/phase-2-functional-spec.md` §4b).** One row per recurring type of change in the project, naming every artifact that must be touched when it happens — for a WordPress plugin: a new setting touches registration, sanitize callback, default, uninstall cleanup, `docs/reference/`, the guide and the changelog. Keel already carried the rules; this turns them into a checklist specific to the project so no slice re-derives them, and it is the artifact that prevents the characteristic bug of any project with a public surface, a translation layer, a persistence layer and user docs. Read at the start of every slice, satisfied item by item at its test point, extended in the slice that discovers a new change type, and verified against the diff at the Phase 7 gate. On an adopted project it is often the most valuable artifact produced, because that knowledge lives only in the maintainer's head.
- **`docs/threat-model.md` (`references/phase-2-functional-spec.md` §4c) — including what is deliberately NOT defended.** Three sections: assumptions; the defended controls, each carrying a delivery state (`IN PLACE` built and evidenced, `TO BUILD` a named slice will build it, `MANUAL` a human must configure it, `VERIFY` only a real environment confirms it); and the **"Not defended"** table naming each deliberate omission with its consequence and what the user would add if their risk profile needs it. Only `IN PLACE` may be written in the present tense anywhere in the project's documentation. All five security profiles gained a **"Deliberate omissions"** section that seeds this table for their project type.
- **Seven new `scripts/keel-verify` checks (`references/phase-5-development.md` §1a).** Every command cited in `CLAUDE.md`, `AGENTS.md`, the README or `docs/` resolves to a real script or CI step (the documentation cites the script; the script is the truth). Internal doc links resolve and no document is orphaned. Every `[E]` code-map marker exists on disk. Code fences are balanced — an unclosed one silently truncates the document everywhere it is actually read. Every documented hook, filter, action or event name is found in the source, so an extension point that was renamed or never fired stops being invisible from inside the project. And the suppression count is reported and compared against the previous sprint close — growth is not an automatic failure, it is a number that has to be justified.
- **Phase 1 §3a — the competitive confrontation, where the scope now actually closes (`references/phase-1-discovery.md`).** The scan produced the category's baseline and step 3 produced a proposed v1; until this version nothing put the two lists side by side, which is how a v1 ships missing something every competitor has had for years — not because anyone decided against it, but because nobody ever compared. The confrontation presents **every** competitor functionality and external demand, never a curated subset, one row each carrying who has it, its cited demand evidence (or the honest "none found"), a rough per-feature cost and the assistant's recommendation. Then the user is asked **how** they want to decide: add everything (offered with the summed cost, so "everything" is a number and not a mood), add a selection, or — recommended — go through them one by one, deciding **in v1 / Later / never** with the cost visible at the moment of choosing. Every row ends in a recorded decision, **including the rejections**: a "never" becomes a `docs/decisions.md` entry so the same feature is not re-proposed and re-analysed six months later. Where the confrontation moves the scope materially, the honest assessment is revisited before the phase closes. The per-feature numbers feed the preliminary estimate instead of being derived twice.
- **"Every time figure is AI development time" is now an unbreakable SKILL.md principle in its own right.** Keel already based budgets on AI time; this raises it from a budgeting rule to a rule about **every duration the assistant ever states** — an estimate, a per-feature cost, a sprint projection, an offhand answer to "how long would that take?", a line in `docs/`. The unit is always the AI's working hours plus the vibe coder's supervision hours, and it is named every time, because an unqualified number is read as the human-team one and the gap between the two is orders of magnitude rather than a margin. A row that reads "3 weeks" when the truth is "4 hours of AI time plus 1 of yours" does not merely exaggerate — it inverts the decision, and the user drops a feature that was cheap. A human-team comparison is allowed only when explicitly labelled and placed beside the AI figure, never instead of it.
- **"When to stop and ask" (SKILL.md).** Eight rows in one table — the spec silent on a product decision, two artifacts contradicting each other, a dependency of consequence, a change that would contradict a recorded decision, three identical test-point failures, production data or money, anything that looks like a security problem, a required input that does not exist. Stopping is a successful outcome in every one; the failure is a plausible guess presented as completed work.

Its reconstructed code map is marked, and its change map is built from the change types the codebase actually has.

## 5.0.0

Major release, two ideas that share one root: **stop asking a human to do what a machine does better, and stop trusting anyone's memory for what a list can enforce.**

The first idea is testing. Keel already demanded real functional verification and a runnable playground — and then, sprint after sprint, closed by handing the user a numbered script of screens to visit and messages to confirm. That is the assistant outsourcing its own work: it is slow, it is not reproducible, it leaves no artifact, and it silently skips the empty, invalid and permission-denied cases where the bugs actually live. From this version the rule is explicit and unbreakable: **the assistant drives every test it can drive** — filling every field, walking every branch, asserting what the interface really shows, reading back what the machine saw — and the user is asked to touch the product only for what is physically impossible to automate, with the reason recorded from a closed list of eight.

The second idea is application. "Apply Keel to this repo" and "bring this project up to the new version" both failed the same way: a subset got applied, the rest quietly did not, and the omission surfaced only when the user asked why something was missing. The answer is not more diligence — it is a sweep read off `MANIFEST.md` row by row, landing in a project artifact where every applicable requirement carries a state, with a mechanical check behind it. An assistant cannot forget a row it is reading off a table.

### Added

- **`references/test-automation.md`** — the protocol that keeps the user out of the test-runner seat. It defines: the division of labour (what the assistant always drives, and the eight tags — `CREDENTIAL`, `HARDWARE`, `ASSISTIVE-TECH`, `JUDGMENT`, `EXTERNAL-APPROVAL`, `PLATFORM-IMPOSSIBLE`, `PRODUCTION-RISK`, `NO-EXECUTION` — that are the only valid reasons to delegate, with the anti-escape rule that anything else means automating it instead, and the scope rule that a credential blocks one leg and never the whole flow); making the product drivable (stable test identifiers on every interactive element, and the prohibition on faking an accessibility label to make a test pass, since that label is read aloud to real users); the `scripts/keel-doctor` contract; the driver per surface with its screen-stealing verdict; how forms are actually filled, in three shapes each — valid, empty, invalid; the ban on arbitrary sleeps; the read-back duty; the static analysers; accessibility as part of driving rather than a separate errand; the evidence rules; and an honest list of what genuinely cannot be driven.
- **`scripts/keel-doctor`** (`references/phase-2-functional-spec.md` §4d, generated at the Phase 5 scaffold) — the environment doctor, compiled from the technical plan's new `## Environment requirements` table rather than improvised. Three modes: `--check` detects only and never needs privileges, `--plan` prints the exact commands it *would* run without running them, `--fix` runs them after the user's OK on an itemized list they can decline row by row. Four states, not two — `OK`, `TOO OLD`, `NOT OPERATIONAL`, `MISSING` — because "installed but not running" and "absent" are different problems and collapsing them is what makes an assistant propose reinstalling something that only needed starting. Plus `--json` so the assistant reads structured output instead of parsing its own table. Nothing global is installed silently, no licence is accepted on the user's behalf, and what genuinely needs a human is reported as a clear stop instead of attempted.
- **Phase 1 §5a — the environment preflight.** The moment the project type and target platforms are fixed, four questions get answered before anything is planned around them: what must exist on this machine, whether any target platform is impossible here, whether testing will take over the user's screen and on which platforms, and what will need installing. Recorded in `docs/01-discovery.md` under `## Environment & test drivers`. A platform this machine cannot build or test changes the plan, not the schedule — and it is the user's decision, made in minute one rather than discovered in sprint three.
- **`test-driver` subagent** (`references/assistant-config.md`) — drives the interfaces and returns the evidence, with an explicit instruction never to report a criterion as passing because a human said so, and never to propose that the user walk a flow it could have driven itself. Bound to the **mechanical** role, because testing splits across two jobs that were previously conflated: deciding what to test is authoring and wants the strongest model, while executing the tests and triaging their failures is command-running against expectations already written down. Test runs are the most repeated agent invocation in Phase 5 — every slice, every sprint close, every session's freshness check — so this is the binding where a cheaper model pays back most often.
- **`docs/keel-conformance.md`** — the conformance sweep's artifact: one row per applicable `MANIFEST.md` Table 1 requirement, each carrying exactly one state (`present`, `missing`, `declined` with its `docs/decisions.md` entry, `n/a` with the condition that excludes it). A row with no state is an unfinished sweep. Created at Phase 1 step 0a, mandatory at adoption step 4a and at every post-update reconciliation, verified at the Phase 7 gate.
- **SKILL.md — two new cross-cutting sections and two new operating principles.** "Test automation — the assistant drives, the user decides" states the split that governs everything: the user decides what gets built, the assistant proves it works. "Applying Keel completely" defines the six-step sweep and its enforcement.
- **Three new `scripts/keel-verify` checks** (`references/phase-5-development.md` §1a): Keel conformance is complete (a `missing` row with no decision, or an applicable requirement with no row at all, fails the run); every user-visible acceptance criterion has either a driven test or a tagged delegation (the mechanical end of "the user will check it"); and interactive elements carry their test identifiers rather than binding to localized visible text.

## 5.2.0

Keel already sent the right checks to the right verifiers. It just ran them in a queue. Every gate read as a sequence of independent passes, each waiting on an answer it never needed from the one before it, and a twelve-screen fidelity walk was twelve serial checks inside a single agent. Nothing was wrong with the verification; the wall-clock was simply the sum of things that had no reason to be added together. This release makes parallel the default and serial the exception that has to justify itself.

### Added

- **A canonical fan-out rule** (`references/assistant-config.md`, "Parallel fan-out"), defined once beside the nine verifiers and pointed at from every phase that invokes them — the same define-once discipline the agents, the rules and the model binding already follow. It names the two shapes fan-out takes and the only four cases where serial is still correct.
- **The reading/executing split that makes parallelism safe.** `code-reviewer`, `security-auditor`, `docs-verifier`, `guide-qa` and `design-fidelity-auditor` only read, so any number of them run together. `playground-qa`, `test-driver`, `a11y-auditor` and `launch-verifier` also EXECUTE, and executing means holding a shared environment — containers, ports, one database, one seed dataset, one origin — so at most one of them runs per environment, with the reading block alongside. Two agents holding one playground is not parallelism, it is contention: a teardown landing mid-suite makes `test-driver` report connection failures and 5xx the product never had, and the rules then oblige it to fail on them.
- **Per-unit fan-out where the work is one check repeated over independent units:** one `design-fidelity-auditor` per screen at the Phase 4 fidelity walk, one `guide-qa` per locale at the Phase 6 guide check, one agent per audit dimension in the adoption gap audit, one reviewer per rubric domain at Phase 2 §6a where a rubric is already on record. Phase 1's one-subagent-per-competitor scan was already exactly this, and is now named as the precedent rather than left as a local habit. The rule carries its own guard: **a per-unit split never silently drops the cross-unit checks** — one extra whole-artifact agent takes them, or they disappear with the split and nobody notices. The worked example is the guide, where secondary-locale mirroring and the theme checksums are exactly what no single-locale agent can see.
- **Capture once, compare in parallel** — the rule that keeps per-unit fan-out from colliding with the one-executing-agent-per-environment limit. Where the repeated check needs a running environment, ONE pass produces the artifacts (the rendered screens at the declared breakpoints, the crawl output, the tooling report) and the per-unit agents read those artifacts concurrently, as readers. That is what makes a twelve-screen fidelity walk one round instead of twelve without putting twelve agents on one browser, and it is why `design-fidelity-auditor` stays a reader: Phase 4 already captured the screens before it is dispatched.
- **Merging as an explicit duty of the main session.** Each agent returns findings for its own slice and nothing else; the session deduplicates by `file:line` and reports once, and the gate is judged against the merged set — never against whichever agent answered first, and never against a partial set because one is still running. This is the failure mode a fan-out introduces that a chain never had, so it is written down where the fan-out is.

### Changed

Two bullets that read like a sequence become one dispatch with a stated reason: the candidate does not change between them.

A throttled request and a broken page look identical in a table.
- **The hotfix gate fans out** (`references/maintenance.md`). Its step is titled "the full gate, fast" and was the one place where speed is the stated goal and the speed rule was absent. Fast now means fanned out, never trimmed.

Existing projects pick it up at the next lock-freshness refresh — which is why this ships as a version rather than as an edit.

## 5.3.0

Chats stop handing over by copy-paste. A session that ends mid-work already composed a self-sufficient continuation prompt and showed it; now it also writes that prompt to a fixed path in the repository, so the next chat can be started by pointing at a file instead of by moving a wall of text between two windows. Everything else in this version exists to keep that file from becoming a lie — including the parts that were written wrong first and corrected by testing them on a real machine before release.

### Added

- **`docs/continuation-prompt.md` — the continuation file.** Written at every session end and every sprint close, always at that exact path, overwritten each time, and listed in `.gitignore` because it is ephemeral session state rather than project history. The fixed path makes the hand-off addressable by a short constant instruction and removes every length limit from what can travel between chats, because what travels is a path. Showing the prompt in the chat does not stop — the file is in addition, never instead.
- **A freshness header**, carrying `Repo`, `Generated`, `Keel`, `Commit`, `Tree`, `Position` and `Handover` (`clean`, or `blocked:` with the reason). The timestamp lives in the header rather than in the filename deliberately: a dated filename would change the path on every write, and the header plus the file's own modification time answer "was this written just now or three days ago?" at no cost.
- **`Repo` — the root-commit hash — and an ABSOLUTE launch path, which are one fix in two halves.** The filename is identical in every Keel project. A chat opened in the wrong window therefore reads THAT project's hand-off, where the commit really is its `HEAD`, the position really is its `PROGRESS.md` and the timestamp really is recent: nothing is stale, and the session continues the wrong project coherently and unsupervised. So every launch passes this repository's absolute hand-off path, making the right file get read; and `Repo` — the stable identity of a repository, unlike a remote URL, which may be absent or plural — makes a session that finds itself elsewhere stop and say so. Neither half is sufficient alone, which is why both are mandatory.
- **The courier rule, with its checks graded honestly.** The file is a courier and never a source of truth. Five checks are mechanical and a script can enforce them — containment first (see below) — `Repo` against `git rev-list --max-parents=0 HEAD`, `Commit` against `git rev-parse HEAD` (with `git merge-base --is-ancestor` reporting how far behind, which beats a yes/no), and `Generated` against both the clock and the file's `stat` mtime, which the header cannot forge. `Position` is a human-readable corroborator and is explicitly NOT claimed as a check: prose against prose is not executable, and a check that cannot be run is a promise. A missing file is not an error at all.
- **Optional chaining of the next chat, and the `Chaining:` project-card line** — `off` (the default), `prefill` (the next chat opens with the prompt already typed; the user presses Enter) or `start` (it launches and submits). The values name the BEHAVIOUR rather than the mechanism on purpose, because one tool family does both: Claude Code's URI handler pre-fills and never submits, while its CLI, started with a prompt argument, submits immediately. A single value meaning different things on different tools is the ambiguity this skill refuses everywhere else.
- **A tool registry with three evidence tiers** — VERIFIED, DOCUMENTED-BUT-UNTESTED, NONE FOUND — because "documented" and "verified" are not the same claim. Only a VERIFIED row is ever acted on; documented-but-untested is a lead telling whoever verifies it where to start. Claude Code holds both verified rows today (VS Code extension → pre-fills; standalone CLI → submits, and inherits `cwd`, so it cannot land in the wrong repository). Cursor, Codex and Gemini CLI are recorded as documented-but-untested with what their documentation actually says; Copilot and Windsurf as none found. An unrecognised tool is never a failure — it is the print row.
- **A containment check, because a repository is not a directory.** Two checkouts of the SAME repository at the same commit — a `git worktree`, a second clone, a copied or synced folder — share their root commit AND their `HEAD`, so `Repo:` and `Commit:` both pass while the session works in the wrong directory. That is the original flaw in a narrower disguise, and worktrees are not exotic: agent harnesses create them routinely. The hand-off's real path must lie inside this session's own `git rev-parse --show-toplevel`, and that check runs FIRST because it is the only one that separates this case. Demonstrated on a worktree, a second clone and a plain copy, all of which passed every other check.
- **`Tree: clean` / `dirty (N files)`**, from `git status --porcelain`. `Commit:` says nothing about uncommitted work, and the session most likely to leave some is precisely the one writing a hand-off while running out of context — so the next session would inherit changes it believes do not exist.
- **`scripts/keel-handoff-verify` — the courier checks stop being prose and become an artifact.** A session composing them itself writes one line of nested `$(...)`; the permission matcher cannot decompose it, returns `Parse error`, and the project's allow-list is bypassed even though every git command in it is allowed — at every link of a chain, not only the first. Measured twice in real sessions. The five checks therefore live in a generated script with ONE allow-list entry, `Bash(./scripts/keel-handoff-verify:*)`, printing a line per check plus `VERDICT: CONTINUE|STOP`. Keel already does exactly this with `keel-verify` and `keel-doctor`, and its own rule says a check that cannot be run is a promise — which is what the courier checks were until now.
- **The single-lane lock, and `start` gated on it.** Chaining was tested rather than reasoned about, and a three-link chain produced FOUR live sessions and four windows in sixteen seconds: two launches were still in flight while the counter was read, so the cap was passed by design. Two sessions on one checkout means interleaved commits on one branch, `PROGRESS.md` overwritten by whoever finishes last, and edits made on reads the other already invalidated — and no courier check fires, because it is the same repository, the same starting commit and a genuinely fresh hand-off. The lock is taken by the ARRIVING session (a launcher cannot know who else is in flight — precisely what failed) and lives OUTSIDE the repository (a brake the chain can `git clean` is not a brake). Until a project has it, `start` is not offered — as a gate, not a warning.
- **`/clear` in the same window, named as the common case it is.** The skill spoke only of "the next chat" and never of the situation that actually occurs most: the window is fine, the context is full. `/clear` starts a fresh session in place and then reads the hand-off — same window, same repository, permissions already granted, the wrong-window failure impossible by construction. It is the safest route and the least automatable (nothing lets a session clear its own context), which is why it is now stated rather than left implicit.
- **The `Chaining:` question is asked at Phase 1 with its warning attached**, in full wording, instead of being filled in as a silent card field. Two things the user must know BEFORE choosing: `start` moves development to CLI sessions rather than their editor (the VS Code URI pre-fills and its handler accepts no parameter that changes that), and `start` removes the only participant who can notice the chain has forked.
- **`scripts/keel-continue` and its contract**, generated at the Phase 5 scaffold on projects whose card is not `Chaining: off`: resolve the repo root and emit an absolute path, refuse a missing or `blocked` hand-off, detect the tool, downgrade to what the card allows but never upgrade, fall back to printing on any non-zero exit, and exit 0 on every path that leaves the user with a chat or a prompt. It writes nothing and decides nothing, which is what keeps the mechanism testable without any editor at all.

### Changed

- **A blocked close-out never chains.** If a session ends on any "When to stop and ask" row, a failed test point, an open Design Request, or the three-attempt rule, the file is still written — with `Handover: blocked` and the reason — and nothing is opened. Chaining a blocked state hands the next session a problem dressed as an instruction, and the next session cannot tell the difference.
- **`start` is opt-in per project, and the reason is stated rather than assumed.** The protections that matter survive without a human keystroke: a blocked hand-off never chains, and a stale or foreign one is refused on reading — all machine checks. What a keystroke uniquely guarded against was landing in the wrong repository, and the absolute path plus `Repo` close that instead. What remains is real but smaller: a window begins working unsupervised from a hand-off composed by a session that was running out of context. That risk is not uniform across projects, so it is the user's call, recorded on the card and in `docs/decisions.md`.
- **`.gitignore`'s unconditional entries** now include `docs/continuation-prompt.md`, alongside `CLAUDE.local.md`, `.claude/settings.local.json` and `.keel-update-check` — in all four places that enumerate them: the Phase 5 scaffold, `references/assistant-config.md` (entries list and definition of done), the manifest's Table 1 row, and the Phase 7 `.gitignore` section.
- **The Phase 5 sprint close-out (step 9)** writes the file and sets `Handover:` as part of the close, and chains only when the card allows it and the hand-off is clean.
- **The portability lock carries the duty, as its own UNBREAKABLE numbered item.** `CLAUDE.md` and `AGENTS.md` previously mentioned the continuation prompt as a trailing clause of the commit item; it is now item 5 in its own right — produce it, show it, write it, verify one before acting on it, chain only when allowed and clean, and never end without leaving something to continue from. It says explicitly that running low on context is when this is most likely to be skipped and most expensive to skip, so it happens BEFORE the session is exhausted rather than as an afterthought. This is what makes the duty reach environments where the Keel skill is not installed at all. The lock block changed, so every project refreshes it at the next lock-freshness check.
- **`Chaining:` joins the project-card template** in `references/project-state.md`, not only the manifest's list of card lines.
- **The hand-off is tool-agnostic; only the auto-open is not, and the skill now says which is which.** `docs/continuation-prompt.md` needs no integration from anybody: "read this file and continue" is an ordinary prompt, so Codex, Copilot, Cursor, Gemini CLI, Windsurf, a web chat or a human typing it all consume it identically.

### Fixed

- **The VS Code surface was identified by an environment variable that is not set there.** The registry's first draft matched `TERM_PROGRAM=vscode`; measured on macOS, Claude Code's VS Code extension sets `CLAUDECODE=1`, `CLAUDE_CODE_ENTRYPOINT=claude-vscode` and the `VSCODE_*` family, and `TERM_PROGRAM` is unset — while the standalone terminal sets `CLAUDE_CODE_ENTRYPOINT=sdk-cli`, `TERM_PROGRAM=Apple_Terminal` and no `VSCODE_*` at all. The condition could never have matched, so detection would have silently fallen through to printing. It failed safe, but it was a guess, made in the same version that forbids guessing about other vendors' tools — which is why the rule "a row is promoted only from an observation on a real machine" is now written beside the table with this mistake named as its reason.
- **The two branches were the wrong way round.** The URI branch was promoted as the safe default and the CLI branch gated behind verification; testing showed the URI neither automates (it waits for Enter, correctly) nor targets the right repository (it lands in the active editor window), while the CLI submits and inherits `cwd`. The gate was still the right call: verifying it is what revealed that the CLI submits outright, so offering it as an equivalent of pre-filling would have been a false promise.
- **"Only Claude Code has an action" was true of Keel's registry and false about the world.** Cursor documents the same mechanism with the same semantics. The claim is now scoped to the registry, and Cursor is recorded at its real evidence tier instead of being lumped in with tools that have none.
- **`Chaining: vscode` survived in the Phase 5 sprint close-out** after the values were renamed — a condition that could never be true, so a sprint close would never have chained at all.
- **The `.gitignore` entry was missing from the Phase 7 release section**, the fourth place that enumerates the same exclusion list.
- **Two commands were conflated where they do different jobs.** Firing a URI (`open` / `xdg-open` / `Start-Process`) serves `prefill`. Opening a VISIBLE CLI session is something else: on macOS `osascript` driving Terminal.app, verified; on Linux and Windows, unverified. An implementer reaching for the plain open command to satisfy `start` ships the headless variant, which runs the next session correctly and opens no window — the user waits for a chat that does not exist and nothing reports an error. `start` therefore resolves on macOS only today, and says so.
- **The `Generated:` check was called mechanical while being a string comparison.** The header writes `+02:00`, `stat` reports `+0200`; the same instant compares unequal, so a script reports tampering on every single run — a model reading them silently does the right thing and never surfaces the trap. Both sides normalise to epoch first.
- **`Repo:` had three silent failure modes in the command that produces it.** A SHALLOW clone returns the grafted commit rather than the root, with exit 0 and no warning, and the value changes after `git fetch --unshallow` — so a hand-off written in CI under `--depth 1` carries an identity no full clone accepts, and the same directory rejects its own hand-off once deepened; `git rev-parse --is-shallow-repository` now gates it and the field is written `unavailable (shallow)`. A repository with TWO root commits prints several lines, which a naive `$(...)` turns into an 81-character value that can never match a 7-character header; `| sort | head -1` picks one stably. And `Repo:` was described as identifying the working directory when it identifies the repository — corrected, with the containment check added to cover what it cannot.
- **The CLI registry row was pinned to the one entrypoint value that had been measured.** `CLAUDE_CODE_ENTRYPOINT=sdk-cli` came from a session launched programmatically; a person typing `claude '<prompt>'` reports `cli`, so the row would have missed the most ordinary case there is, and the vendor may add more. Matching is now asymmetric: `claude-vscode` by name, because it is the only value whose behaviour differs, and everything else with `CLAUDECODE=1` treated as the CLI. Measured on macOS in the process: the extension sets NO `TERM_PROGRAM` while the integrated terminal sets `TERM_PROGRAM=vscode` — so that variable identifies the terminal panel, not the extension, the exact inverse of the first draft's guess — and `VSCODE_*` turns out to be two disjoint families (`VSCODE_PID`/`VSCODE_IPC_HOOK`/`VSCODE_ESM_ENTRYPOINT` in the extension host, `VSCODE_GIT_ASKPASS_*`/`VSCODE_INJECTION` in the terminal). Three surfaces, overlapping variables, one reliable discriminator.
- **The CLI registry row excluded on `VSCODE_*` and would have stopped matching inside VS Code's integrated terminal**, a shell that inherits the editor's variables. The behaviour is a property of `CLAUDE_CODE_ENTRYPOINT`, not of the parent process: the CLI submits and inherits `cwd` whether it was launched from a terminal app or from a panel in the editor. Matching is now on the entrypoint alone, with `VSCODE_*` demoted to a corroborator that is never used to exclude. The integrated shell's entrypoint value remains UNRECORDED rather than assumed — it either matches the CLI row or prints, and both are safe.
- **The `keel-continue` contract contradicted an UNBREAKABLE rule and left three things to invent.** Its point 2 said to refuse a `blocked` hand-off and print why, while the prompt rule says the prompt is printed whenever a chat cannot be opened, for ANY reason — an implementer had to guess. It now prints the reason AND the prompt, marked blocked, and exits 0: refusing to chain and refusing to print are different things. "Downgrade, never upgrade" was unexpressable when the tool's row has no action at the resulting tier (the CLI row knows only `start`), which now prints. And the contract verifies containment, `Repo` and `Commit` BEFORE firing rather than after — under `start` there is no human between the launch and the work, so discovering a mismatch post-launch is the wrong order. Percent-encoding, the per-platform clipboard commands, and "a malformed header is treated as a missing file" are now specified rather than left to the implementer.
- **`scripts/keel-continue` was required by the manifest with nothing defining its contents**, unlike `keel-verify` and `keel-doctor`. Declaring a required artifact without a template is the "declared is not delivered" defect this skill exists to prevent, committed inside the version that hardens that rule; it now carries a six-point contract.

## 5.3.3

Two behavioural fixes, both found by building the thing that would have exercised them. Nothing new is designed and nothing migrates.

### Fixed

- **The conformance sweep was reading its own previous output.** Run as a real fan-out over a project, the sweep's agents cited the `docs/keel-conformance.md` already on disk as evidence for their own verdicts. ## 5.4.0

One idea: Keel learns what its environment can actually do, and orchestrates accordingly. The preflight stops assuming, the dispatch rule gains the step above subagents, and a round of orchestration research is banked as three rescued findings and three closed doors.

### Added

- **The environment preflight probes the `claude` command instead of assuming it.** Where the project card says `Chaining: prefill` or `start`, Phase 1 §5a now runs `command -v claude`, offers the platform's install command when it is missing (macOS, Windows and Linux commands are written down), and records the answer either way; declined or unavailable means `start` is not offered and `prefill` is the maximum, naming the requirement that failed. v5.3.2 named the CLI as the fourth gate on `start` and left nobody to check it, which put the discovery at the first close-out of a chain — under `start`, precisely when nobody is watching.
- **Protected environments are announced up front instead of discovered on failure.** The preflight now asks what this session's environment CANNOT do and says it in one line at Phase 1, beside the English-docs default and the accessibility commitment. The measured case is Cowork's device bridge, and every item was hit for real during v5.3.x: the bridge cannot delete files (`rm` returns `Operation not permitted`, and the `.lock` files git leaves then block the user's own repository), it has no network, it exposes no `localhost` of the user's machine, it offers no screen control, and the cloud container that DOES have network cannot see the user's files — so neither half can execute where the repository lives and reach the network at once, which is exactly what playgrounds, installs and test runs assume. A protected environment is a fact about the session, not a failure; saying it late is what makes it expensive.
- **`NO-EXECUTION` gains its partial case.** The tag described a session with no execution at all. The measured environment is neither that nor fully capable: it can execute, it can touch the files, but not both together, or not with a network. That case now has language — say which half is missing, tag per LEG and never per session, and drive everything the session genuinely can drive.
- **The verifier dispatch rule gains its three-step fallback chain:** workflow (where one exists and the user has opted in) → parallel subagent block (where subagents exist) → inline and serial. All three produce the same table; only the wall clock changes, and none of them drops a check. A workflow tool needs explicit opt-in, may be absent, and carries a user-controlled size cap Keel does not govern — identical in kind to the subagent situation the standing fallback already handles, which is why it is written as a chain and never as a requirement.
- **The conformance sweep is written up as the canonical workflow shape**, measured on a real project: 31 rows, 5 agents, 110 seconds, no hallucination found when the evidence was contrasted against the disk. With a per-row schema no MODEL sits between the data and `docs/keel-conformance.md` — but the claim is stated honestly rather than sold: two pieces are still needed, a deterministic template in the script (about six lines, no model) and a way to reach the disk, since the script has none — either a writing agent forbidden to change a word, or, cleaner and one agent cheaper, the workflow returns the markdown and the main session writes it. "No post-processing" means no model in the middle, not no code. Dedup becomes a function instead of a discipline, the concurrency cap is native, and the cross-unit check becomes an explicit extra agent visible in the script rather than trusted to memory. What stays judgment is said too: which verifiers a gate calls for (six of the nine agents are conditional), the reader/executor split, `test-driver`'s ordering exception, and the gate's verdict.
- **A rule for fanning work out over git worktrees, and it inverts a Keel rule on purpose.** Dispatched at the Phase 5 sprint kickoff, which names who dispatches, who writes the report and when (`references/phase-5-development.md` §0) — the rule itself lives in `references/project-state.md`, and the phase reference is what makes the artifact actually get created on a new project. The living state is written by the session that owns the MAIN tree; a worker in a worktree writes `docs/.keel/slices/<n>.json` (`slice`, `status`, `branch`, `commit`, `needs_user`) on its own branch and never the state. Measured: with the workers writing `PROGRESS.md`, the code merged clean every time and the state file conflicted in 100% of merges, N−1 times for N workers — with the report file instead, three merges and zero conflicts. `merge=union` in `.gitattributes` is recorded as dangerous rather than merely useless: a state file that is REWRITTEN rather than appended merges cleanly into a corrupt one, two contradictory position lines and no conflict marker. The worker's close-out contract is fixed in order — commit → report → atomic done-signal (`printf > tmp && mv`, because a rename cannot be read half-written) — so an existing signal implies committed work and never the reverse. Not stdout: `claude -p` writes nothing until the end, so a live worker and a dead one both show an empty log. A `blocked` report is not merged; its question goes to the chat where a person is. New conditional MANIFEST Table 1 row for the slices path.
- **`claude agents --json` is recorded as the supported way to see live sessions** — pid, cwd, kind, session id, name, and `idle`/busy — replacing any parsing of `*.jsonl` transcripts, with the caveat that must travel with it: **`-p` sessions do not appear**, only interactive and `--bg` ones, so it is not a completion detector for print workers. `--session-id <uuid>` lets a launcher assign the id up front.

- **The repository's own release linter gains check 9: every MANIFEST Table 1 row required AT A PHASE is named by that phase's reference.** This is the shape v5.3.1 fixed and that recurred inside this very release — a requirement recorded in the index with no phase reference telling anyone to create it, so by the manifest's own authority rule the artifact is never created on a new project and only the reconciliation produces it. Run against the v5.3.0 tree the check fails on `scripts/keel-handoff-verify`, turning a release that shipped "Releasable" into a blocked one; run against this tree it is clean. Two false negatives found while building it are worth recording, because any future check over these tables inherits both: splitting rows on `|` without unescaping `\|` shifts the columns and the check passes without verifying anything, and accepting a bare directory basename let `docs/.keel/slices/` through on the word "slices", which Phase 5 uses in every paragraph for vertical slices. Three rows are exempt through an explicit list rather than a generic two-hop rule — the convenient generic version lets the v5.3.0 defect through — and one gap stays open in the file rather than silently unhandled: rows whose "Required from" is an event rather than a phase have no owning reference to check against. Prose did not stop this shape twice; the check runs on every tag.

### Changed

- **File isolation is not environment isolation.** Where a harness offers to run each agent in its own worktree, what it isolates is FILES. The serial case it might appear to dissolve is about two EXECUTING verifiers sharing one port, one database, one seed, one origin — and two worktrees fight over all four exactly as two directories in one checkout would. "One executing verifier per environment" stays a serial stage whatever the isolation mechanism offers.

### Rejected — measured, and recorded so they are not re-proposed

- **The chat director — a second chat whose role is orchestrating worker chats — is abandoned as a design.** It works: three slices, three workers, zero conflicts, the state written by the director alone, and a product question escalated instead of invented. It still does not earn its scaffolding. It costs ≈7k tokens of context per slice in a toy and 15–20k in a real project — a `PROGRESS.md` of 4–18 KB read and rewritten every slice is what fills it, not the waiting loop, which is one Bash call returning one line however long it blocks — and therefore degrades between the 6th and the 9th slice. No cost accounting, no cancellation, no concurrency cap, all to obtain parallelism the native primitives already provide with all three. Its one real advantage, a chat with a person in it that can be asked a question and can answer, is obtained by something much smaller: one ordinary Keel session that, in a single turn, dispatches N workers into worktrees, waits for their signals and merges. The chat where the person is, is the chat you are already working in. The negative result is the useful result of the round, and the formula built to prove it is what was kept.
- **`claude --resume` as a mailbox into a live session.** There is none. It starts a new process that reads the transcript from disk: against an idle session the target's window sees nothing, and against a session mid-turn the transcript forks, a `Continue from where you left off.` / `No response requested.` pair that nobody wrote is fabricated, and the message vanishes silently from the resumable history. It is also scoped to the current directory's slug, so a worker in a worktree could not reach the main tree's session even if the mechanism worked.
- **Closing another session's window from a script.** Measured on macOS: 40–78 seconds with no confirmation and no error either way, a hard kill in which no cleanup hook runs at all (three signal traps installed, none fired, the log never created), and therefore a guaranteed orphaned lane, since the holder can never release it. Opening an unrequested window was already placed behind the user's decision; closing one is more destructive and the mechanics are worse. Not even opt-in.

**The lock block's content did not change**, only its version stamp, so the refresh at the next freshness check is a stamp-only rewrite.

One idea: v5.4.0 wrote down a fan-out and never wrote down how to start one, and it gated the CLI probe on the wrong question and then trusted the probe too much. Three fixes, no new artifact, nothing to migrate.

### Fixed

- **The fan-out gains its dispatch command, which v5.4.0 specified everything around and never wrote.** `references/project-state.md` recorded who writes the living state, the worker's report file, the close-out contract in its fixed order and the blocking wait, and left the reader with a contract to satisfy and no way to begin: neither `git worktree add` nor any launch appeared anywhere in the skill. The new "Dispatching a worker" section carries both, plus what the two flags are for — `--session-id` assigns each worker's id up front instead of looking it up afterwards, and `--permission-mode bypassPermissions` is what lets an unattended worker finish, which is exactly why a fan-out is dispatched only from a session with a person in it, only over slices approved at the kickoff, and only into worktrees of this repository. Phase 5 §0 now points at the command and states the precondition it needs.

This is the shape v5.3.2 fixed for `start` ("named the CLI as the fourth gate and left nobody to check it") recurring inside the release that introduced the fan-out. The step now asks both halves, is not applicable only when BOTH are false, and records the answer for both consumers: no working CLI means `prefill` is the maximum AND the sprint is built serially in the session — a slower plan, not a degraded one.

That is the same class of bug as collapsing `NOT OPERATIONAL` into `MISSING`, and it spends the user's machine rather than their patience. The reverse is now stated too, and it was measured on a real install: `npm install -g` accepts a package whose `engines` demands a newer runtime than the active one and emits only an `EBADENGINE` warning, so the binary lands on `PATH` and whether it runs is still unknown. A positive is followed by the tool's own version probe against the requirement, and records `TOO OLD` or `NOT OPERATIONAL` rather than `OK`. Phase 1 §5a applies both directions and prefers the native installer, which bundles its own runtime, where the user's is managed by a version manager or a conda environment and can change under them.

## 5.5.0

Keel stops working in the dark: it settles what it is allowed to do before it starts, and it tells the developer when it stops.

### Added

- **`references/notifications.md` — out-of-band notification, so a stop reaches a human.** Keel halts on purpose ("When to stop and ask" makes stopping a successful outcome), but a blocked session and a working session look identical from outside: the chat sits there, the developer is elsewhere, and a thirty-second question costs an afternoon. The new reference defines the channel that closes that gap, and its central rule is **a channel counts only if it DELIVERS**. That is not a hypothetical distinction: the Gmail connector commonly available to a session exposes `create_draft`, `update_draft` and `list_drafts` and **no send operation**, so "notified by email" after creating a draft is a false claim of exactly the kind "declared is not delivered" forbids — and it fails precisely when nobody is watching, which is the only case the mechanism exists for. Candidates are therefore classified before use (delivering / compose-only / in-chat only), with **the environment's own notification tool as the preferred default** — no address, no credential, no server, so it is the only channel already true on a fresh machine — and two of its properties written down because both are easy to misread: it reaches the desktop always and the phone only while the harness's remote control is connected (so it covers "walked away from the desk", not "out of the building"), and it deliberately does not fire while the user is at the terminal, reporting "not sent", which is this reference's own anti-noise policy one layer down and therefore counts as delivered-or-redundant rather than as a failure to escalate. The capability is PROBED each session rather than read off a tool list (a connector can be listed and unauthorized; a headless or scheduled run usually has neither), and "no channel available" is a stated result rather than silence. The reference also fixes the triggers — a blocking stop, a blocking delegation tag, a deploy the developer must make, a blocked hand-off — and the anti-triggers, because the failure mode of a notification system is never too few messages but a person who has learned to ignore it. What the message carries is bounded by the confidential-data rule: a channel is a wider exposure than a repository, never a narrower one, so no credentials, no customer data, no source blocks — the project, the position, the one-sentence blocker, and where to continue.

### Changed

- **The session opens with three questions in one batch, asked once and recorded.** `SKILL.md` gains "Session start setup", executed with the maintenance block and before the entry-mode decision: automatic mode yes or no, whether Keel works the forge issues at every sprint close, and how it reaches the developer out of band. The answers land on new project-card lines — `Autonomy:`, `Branches:`, `Notify:` — plus a decision entry, and no later session asks again. **Everything hangs off the first answer, and it is never inferred per action:** automatic means Keel does not ask and performs every merge to the integration branch and every push itself; not automatic means the opposite regime in full — it asks every time and pushes nothing that was not explicitly requested, with the unpushed commits named in PROGRESS.md so the queue is at least visible.
- **`manual` permission mode is now resolved before any work, because it makes the rest of the skill impossible.** In Claude Code's default mode a command is matched STATICALLY against the `allow` rules, so anything composite — a shell variable, a `&&`, a `;`, a pipe — opens a dialog even when every command inside it is allowed, and Keel's phases are made of exactly those commands. The result is not slower work, it is stopped work. `references/keel-maintenance.md` gains the full procedure: the preferred persistent route (create or MERGE `.claude/settings.local.json` — `defaultMode: "auto"`, a minimal `deny`, `env.PATH` — never removing or reordering a rule the user put there), the per-session alternative (`--permission-mode auto`, or Shift+Tab), and the `.gitignore` verification. This is the single exception to "Keel never creates a personal config file", and it is narrow by construction: that file is machine-local and gitignored, so it binds this checkout and nobody else, whereas the COMMITTED `.claude/settings.json` still requires the user's explicit confirmation — `references/assistant-config.md` now states both sides so the two rules cannot be read as contradicting each other. The mode is the user's decision; writing the file that implements it is not a second question.
- **`env.PATH` is written expanded and absolute — never `${PATH}`, never `$HOME` (measured on a real machine, mid-release).** The field is consumed literally: a value ending in `:${PATH}` appends the seven characters `${PATH}` rather than the existing PATH, and `$HOME/...` names a directory that does not exist. What gets lost is the base system directories, so `/usr/bin` and `/bin` vanish and `git`, `ls`, `cut` and `grep` stop resolving in every session and every project until someone edits the file — and the symptom reads as `command not found: git` on a machine where git obviously works, which is precisely the false `MISSING` the doctor's corroboration rule exists to catch. The recipe now enumerates every directory literally, system ones included, and the procedure says to resolve the real value in the user's login shell and write the RESULT rather than the expression that produced it — plus to inspect any existing `env.PATH`, including the user-level `~/.claude/settings.json`, and repair an unexpanded one in the same breath, because that one poisons every project on the machine rather than a single repo. The earlier draft of this release shipped the broken form.
- **Keel never prefixes a command with `export PATH=... && ...` again.** With `env.PATH` in the settings file the tooling already resolves, and the prefix ALONE makes the command composite — forcing a dialog on every single call, including calls that would otherwise have matched an `allow` rule cleanly. The rule covers tool calls, generated `scripts/` files, phase references and commands handed to the user; an unresolvable tool is answered with its absolute path (recorded in the environment requirements table), never with a PATH prefix. The milder form — `cd <dir> && <command>` where the tool already takes a working directory — has the same fix.
- **A forge issue is answered in three beats, and Keel never closes one (UNBREAKABLE).** The previous rule tracked issues honestly and left the reply as a single event, which is wrong by two beats: the code changing and the reporter being able to try it are different events, usually days apart. So — (1) fix landed: comment what was wrong, that it is implemented, and that they will be told when it is testable; status `awaiting deploy`; **not closed**. (2) The DEVELOPER is notified through the recorded channel that a build or deploy is needed before the reporter can test — a real stop, recorded in PROGRESS.md, with Keel waiting. (3) The developer confirms it is up: comment again, naming the version and what to look for; status `awaiting reporter`. The reporter's answer closes it or reopens the work, and if the reporter or developer already closed it, Keel leaves it closed and records who did. `docs/issues.md` gains the two statuses and the `Replies:` / `Deploy:` / `Closed by:` fields, so a fresh session can tell beat 2 from beat 3 without reading the forge thread and guessing. Phase 5's sprint close gains step 8, and its inbound half is deliberately TWO sweeps — new issues, and **new comments on issues that already exist**, the half that is easiest to skip and most expensive to skip, because a log recording only what Keel published is a monologue: a comment on an issue in `awaiting reporter` IS the verdict that closes it or reopens the work, and it may not sit unread until someone notices. The outbound half cross-checks against commits and change-maps, never recollection — and a "fixed" claim needs the same evidence as any other claim in that phase: the commit and the regression test); `references/maintenance.md` carries the same lifecycle into post-release, where the gap between shipping and confirming is widest.
- **`develop` integrates, `main` is the person's, and the assistant does its own pushing (UNBREAKABLE).** `SKILL.md` gains a cross-cutting "Git flow" section that separates two things which get confused constantly: **publishing work so it is not lost is the assistant's job; releasing work to users is the person's.** Withholding a push does not create review — it creates a queue nobody owns, invisible to every other checkout and dependent on someone remembering; the observed symptom was a PROGRESS.md carrying several entries marked "PENDING push". So: the integration branch (`develop`) is created from `main` and published if absent; work branches start from it, never from `main`; in automatic mode the assistant merges them back and pushes, both halves, without asking; and the assistant **never** merges `develop` into `main`, never tags and never publishes a release on its own initiative — those need an explicit instruction in the current conversation, the same shape as the version-change policy and for the same reason: they are what real users receive. When `develop` holds work ready for production, Keel says so under "Ready for `main`" in PROGRESS.md and in the hand-off, and stops there — signalling IS the action. One deliberate exception, which is not a loosening: a production hotfix branches from the RELEASE TAG (users run the tag), merges back to `develop`, and still never reaches `main` without the user. Phase 5's sprint close gains the merge-and-push step, Phase 7 opens by naming who performs the release, and `references/maintenance.md` reconciles the hotfix branch point. **The rule is checked, not merely written:** `scripts/keel-verify` now fails on commits that never left the machine (`git log @{u}..HEAD`) and on working directly on the release branch — a rule stated only in prose is the trap this skill names elsewhere, and it would have been self-inflicted here. `scripts/keel-handoff-verify` gains the matching `Branch:` row, because the hand-off header grew a field and a field with no check is a promise. **Adoption is not exempt and not steamrolled:** `references/adoption.md` runs the same setup batch, and settles the branch shape WITH the user against what the repo already does — conventions are observed, not imposed — with only "the assistant never merges to the release branch, never tags, never releases" held non-negotiable.
- **Keel finishes the queue instead of asking whether to continue.** A new operating principle: when a block of work ends and the queue holds work that does not depend on what was just done, continue — do not stop to ask, and do not hand back a menu of what is left. Exhausted context is a hand-off, not a decision: write `docs/continuation-prompt.md` and carry on there under the same rule. Keel stops for exactly two reasons, both already in "When to stop and ask" — the next step depends on something not yet done, or the decision is genuinely the person's. "Shall I go on?" is neither; it is the assistant asking the user to do its scheduling, at the cost of a round trip every time.
- **The hand-off says where the code is.** The continuation prompt gains a `Branch:` line in its freshness header (work branch, whether it is merged and pushed, anything awaiting the user's merge to `main`) and three new opening steps: apply the recorded setup rather than re-asking it, read the branch state, and keep going while the queue holds independent work. A hand-off that does not say where the code lives sends the next session hunting for it.
- **One close-out opens one window: the launch receipt (UNBREAKABLE).** Measured on a real close-out — a single session fired the launch four times, four windows opened, three arrived, found the single-lane lock held and politely exited. The mechanism worked exactly as specified and the user still got four chats with no way to tell which was live. The cause is a gap the old design stated openly: the lane serialises **execution** and nothing serialised **launching** (`keel-continue` explicitly did not take the lock, on the grounds that arrivals would sort it out). So the launcher gets its own guard, and it protects an EVENT rather than a resource: a launch is claimed against the hand-off's identity (`Generated:` + `Commit:`), the claim is an atomic `mkdir` rather than a `test -f` followed by a `touch` — the gap between those two is where the duplicate is born — and the receipt lives outside the repository keyed by the real toplevel path, like the lane, so a `git clean` cannot erase the brake on the thing it brakes. Three rules complete it: **a launch is never retried** (an open command's exit code says the command ran, not that a window appeared, and firing again under that uncertainty is exactly how one hand-off becomes four — the answer to "I do not know" is always to print the prompt); **exactly one place in the skill may invoke `keel-continue`**, so a close-out that re-runs hits its receipt and fires nothing; and **a circuit breaker** stops chaining and says so when more than three receipts appear for one repository within an hour, because a loop that announces itself costs a message and one that does not costs a screenful of windows. The two guards now state plainly that they are not substitutes: the lock decides who may WORK, the receipt decides how many windows OPEN.
- **`scripts/keel-doctor` gains a third severity, `advisory`, and its first two rows.** Permission mode and notification channel are reported, never blocking: the work completes either way, but under friction the user should know about. Collapsing them into `blocking` would fail gates over a preference; leaving them out would let a session in `manual` mode degrade the driven-test protocol back into asking the user, which is the failure that reference exists to prevent.
- **The continuation prompt applies the recorded setup instead of re-asking it.** Its first step is now to read the card's `Autonomy:` and `Notify:` lines, resolve the permission mode if the machine is fresh (the settings file is gitignored, so a new checkout has none while the DECISION is already recorded), and re-probe the channel for the current session — a channel that answered yesterday is not a fact about today.

**The lock block's content did not change**, only its version stamp, so the refresh at the next freshness check is a stamp-only rewrite.

## 5.5.1

One flag in the fan-out dispatch, wrong in two independent ways, plus the gitignored file that would have undone the fix.

### Fixed

- **Fan-out workers run under `--permission-mode auto`, never `bypassPermissions` (UNBREAKABLE).** The flag was chosen on the premise that it is what lets an unattended worker finish. **The premise is false and it was measured: `bypassPermissions` asks for confirmation EVERY time** — entering it is itself a gated act, so rather than removing prompts it guarantees one, and the worker sits waiting for an answer nobody will give. It breaks exactly the automation it was picked to enable, and it fails in the direction that looks like a hang rather than an error, which is the expensive direction. The safety argument points the same way and would have sufficed alone: `bypassPermissions` evaluates no permission rules at all, `deny` included, so v5.5.0's session-start step wrote a block to keep `rm -rf /*`, `sudo *` and `curl * | sh` out of reach and the fan-out then handed that exemption to the only sessions that are simultaneously parallel, unattended and writing to real branches — the worst place in the skill to remove a barrier, and the one where nobody is watching. `auto` is not a drop-in and the cost is stated rather than left to be discovered: a worker in `-p` mode that reaches an action the allow-list does not cover cannot be asked, so the call is refused and the slice may fail. That is the correct failure direction — a refusal surfaces in the worker's report and is fixed by extending the allow-list, whereas an unattended `sudo` is fixed by nothing. **If workers stall, extend the allow-list; never go back to bypassing.**
- **The dispatch copies `.claude/settings.local.json` into each worktree before launching.** Found while verifying the fix above, and it silently undoes it: that file is gitignored — which is what makes it machine-local — so `git worktree add` produces a clean checkout WITHOUT it, and the worker falls back to user-level configuration with no project `deny` block, no project `env.PATH` and no project allow-list. The flag would be right and the directory wrong, which is worse than the original bug because it looks fixed. Its absence is invisible at runtime and shows up only as a worker mysteriously blocked, or mysteriously unblocked.

### Changed

- **The `env.PATH` warning gains the symptom that does not look like `PATH` at all: a re-authentication loop.** On macOS the keychain is reached through `/usr/bin/security`, which git and `gh` credential helpers invoke by name. Drop `/usr/bin` from `PATH` and that lookup fails, so the helper cannot read a credential sitting right there — and instead of an error naming a missing binary, the tool asks to authenticate, succeeds, fails to store, and asks again. The user debugs tokens, scopes, two-factor and the forge's settings, none of which is broken. The rule added: whenever authentication loops for no reason, check `PATH` for `/usr/bin` before touching a single credential, and never rotate a token on that evidence — it fixes nothing here and costs whatever else was using it.

**The lock block's content did not change**, only its version stamp, so the refresh at the next freshness check is a stamp-only rewrite.

## 5.5.2

The launch of the next chat, fixed at the four places a real close-out broke it — five windows opened, four killed by hand, and every one of the receipt's protections absent because no receipt was ever claimed.

### Fixed

- **A session NEVER composes the launch itself — it runs `scripts/keel-continue`, or it prints the prompt (UNBREAKABLE).** The courier checks have carried this rule since v5.3.0 ("A session never composes these checks itself"); the launch never did, so the skill said how many times it may be fired and never said what is allowed to fire it. A session that finds no `scripts/keel-continue` — an older project, a scaffold that predates it, a checkout where it was never generated — prints the prompt and stops. It does not reach for `osascript`, `open`, or a terminal of any kind. The absent script is not an obstacle to work around, it is the answer: no script means no chaining on this project yet, which is exactly the `off` behaviour the user already knows how to live with, and regenerating it is a maintenance touch on a later session rather than an improvisation at the end of this one.
- **The `start` action carries `cd '<absolute repo root>' &&`, and the registry's claim that it "inherits `cwd`" is gone.** That claim is true of a direct exec — `claude '<prompt>'` as a child of a session already standing in the repository — and **false of the action this skill actually verified for `start`**, because `osascript` asking Terminal.app to `do script` opens a NEW login shell, which starts in `$HOME` and inherits nothing from the process that asked. The two statements sat six lines apart in the same file and the false one was the reassuring one. Note what does NOT catch this: containment, `Repo:` and the absolute hand-off path are checks the ARRIVING session runs on a file it was told to read, so a session that lands in `$HOME`, reads no hand-off and finds no repository runs none of them — it simply starts inventing, with nobody watching. The `cd` is the only thing between `start` and a chat working in the wrong directory.
- **A launch that fired WRONG is spent, exactly like one that fired unobserved.** "A launch is NEVER retried" was written for "I cannot tell whether a window appeared", and in those words it does not cover "a window appeared and I can see it is wrong" — so the close-out killed the process it had just launched and fired again, four times, each iteration technically honouring the rule because each launch had in fact succeeded. Stated for both cases now: once the launch has fired, this session's chaining is over, whatever the outcome. A wrong window is reported in one line and the prompt is printed. Killing another session's process to make room for a better attempt remains forbidden for the reasons already recorded under "Designs measured and rejected" — no cleanup runs, the lane is never released, an orphaned lock is guaranteed — and it is forbidden even when the killer is the session that fired it.
- **`references/phase-5-development.md` §1 stopped contradicting `references/project-state.md` about what the scaffold generates.** It described `scripts/keel-continue` as "resolve the platform's open command … fire the constant URI once" — which is the `prefill` mechanism — for a script that must also serve `start`, the exact conflation `project-state.md` warns produces the headless variant: the next session runs correctly and no window ever appears. The scaffold line now names the nine-point contract, states that the two tiers do not share a command, and carries the `cd`.

### Changed

- **Quoting is recorded as the second reason the launch belongs in a generated script.** `osascript -e 'tell application "Terminal" to do script "…"'` nests three levels — the shell's quotes, AppleScript's, and the inner command's — around a payload containing absolute paths and a prompt sentence. Hand-composed at close-out time it is a coin flip: the measured close-out got it wrong twice before writing the command to a file and running that instead. A script written once, with the prompt passed through a file rather than interpolated into three quoting layers, has the problem zero times.

**Reconciliation:** regenerate `scripts/keel-continue` at the next maintenance touch on any project whose card is not `Chaining: off` — the `cd` is the change that matters, and a script generated before v5.5.2 does not have it. **The lock block's content did not change**, only its version stamp, so the refresh at the next freshness check is a stamp-only rewrite.

## 5.6.0

The work stops being able to exist in only one place. A project could be started, specified and half-built inside one folder on one computer — no repository, no remote, nothing replicated — and Keel, which has rules about accent marks and minified assets, said nothing about the disk that holds every artifact it produces.

### Added

- **"Work never lives only on this machine" — a new UNBREAKABLE cross-cutting section in `SKILL.md`, and Question 0 of the session-start setup batch, which is now four questions.** It is asked FIRST and answered BEFORE anything is created, because it decides whether the rest of the session's output exists in one place or two. Two things satisfy it and Keel checks both with commands rather than impressions: a Git repository with a remote (`git rev-parse --git-dir`, `git remote -v`), or a tree whose absolute path sits inside a location that replicates off the machine — Dropbox, iCloud Drive, Google Drive, OneDrive, pCloud, Sync, Nextcloud, a network volume — **confirmed with the user, never inferred from a folder's name**. What is missing comes back as a concrete offer, not a warning to nod at: `git init` and the first commit, publishing to the forge the user names (Keel prepares the exact commands and runs them where a forge CLI is authenticated), or moving the project inside a synced folder.
- **`Durability:` on the project card**, recording what covers the requirement — or `NONE — accepted risk (D-0XX)` where the user declined, which is their right and is recorded as an accepted risk with its consequence written out. **A repository with no remote is explicitly a partial answer, not a pass:** local commits protect against a bad edit and against nothing that happens to the disk.
- **Two `scripts/keel-verify` checks**, because a trap closed by prose alone is still open — this skill's own rule, applied to its own new rule. A remoteless repository that carries no recorded decision now **fails** instead of being skipped, which is the inversion that matters: the worst case had been the one case nothing reported. And a dirty working tree fails, naming the files — with the fix stated as the commit, never as a `.gitignore` entry chosen to make the check green.

### Changed

- **Nothing stays uncommitted (UNBREAKABLE), and it is stated where it was previously only implied.** Every working block — a slice, a test point, a sprint close, a session end, a stop of any kind — ends with the work committed to `develop` or to a work branch bound for it, and a repository carrying only `main`/`master` gets `develop` created first rather than product work landing on the release branch. Outside automatic mode the PUSH may wait for the user, as it always has; **the commit never does.** Withholding it leaves the work in the one place that survives nothing, which is the opposite of deferring safely.
- **Automatic mode is deliberately untouched.** The question is asked once and lives on the card; every later session re-runs two cheap commands and says one line if reality no longer matches — it never re-asks, so a removed remote surfaces the day it happens instead of the day it matters. And in automatic mode Keel performs `git init`, the first commit, the creation of `develop`, and every commit and push itself without asking. Only choosing WHERE the work is published — which forge, which account, which folder — stays the person's, because it is theirs to own and not because it needs a permission dialog.
- **Adoption checks it too, and that is where the exposure is largest**: an adopted repository carries years of work, so "it exists only on this laptop" is a far bigger number than on a project born five minutes ago. Adoption also inventories what arrives already uncommitted in the working tree and commits it, after the confidential-data check, rather than leaving it stranded.

**Reconciliation:** answer Question 0 once on every existing project and add the `Durability:` card line, verifying it with commands rather than memory — a repo whose remote was removed is exactly the case this finds. Add the two checks to `scripts/keel-verify` at the next touch on projects that have one. **The lock block changed** — item 4 gains the never-leave-work-uncommitted duty and the no-remote warning — so `CLAUDE.md` and `AGENTS.md` (and any `GEMINI.md` mirror) need a real content refresh at the next lock-freshness check, not a stamp-only rewrite.

## 5.7.0

Closing the laptop at a sprint close stops costing anything. The hand-off was already specified, already written to a fixed path, already verified by a script — and it still failed the one case the user actually lives in: finishing a sprint, walking away, and opening a fresh chat days later with a one-word prompt.

### Changed

- **The continuation file is written at EVERY sprint close, unconditionally (UNBREAKABLE).** The duty existed (Phase 5 §5, step 11) but every surface around it framed the file as a SESSION-END artifact — "whenever the session is ending", "any session ending mid-work produced a continuation prompt", and item 5 of the portability lock in the same words. In automatic mode a session normally carries straight on into the next sprint, so the close was precisely the case the wording did not compel: the moment a person actually gets up from the desk. It now holds in automatic mode exactly as in manual, and on `Chaining: off` exactly as on `start` — **chaining decides whether a next chat is OPENED, never whether the hand-off EXISTS.** Stated in the four places a session reads: `SKILL.md`, `references/project-state.md` (the file's own section, the template intro, the definition of done), `references/phase-5-development.md` (step 11 and the phase's definition of done), and the lock.
- **A hand-off that is not current is worse than no hand-off (UNBREAKABLE)** — the half that was missing entirely, and the half that would have broken the guarantee even with the file written. The courier checks compare `Commit` and `Tree` against the repository, so a file written at a close and then left behind by three more slices comes back `VERDICT: STOP` and the fresh chat refuses to continue: it looks exactly like insurance right up to the moment it is needed. A session that carries on past a close therefore **regenerates it as the work advances** — at every commit point, which in Phase 5 means every test point that commits — and unconditionally before ending. One small overwrite per test point, against the reconstruction the whole mechanism exists to eliminate.
- **Reading the hand-off is the FIRST thing a resuming session does — before the state files.** This is what makes a bare "continue" enough to restart the work, with no recap, no pasted wall of text and no memory of the last session. The fixed session-start order began at `docs/PROGRESS.md`, so the file was only ever consumed when someone pointed a session at it — which works for a chained chat and is useless for a chat opened by hand days later. Now in the Resume entry mode (`SKILL.md`), in the fixed reading order (`references/project-state.md`), and in **item 2 of the portability lock**, so it binds an assistant that opens the repository without the skill installed. A missing file stays ordinary: it is gitignored, so a fresh clone has none, and the normal order simply proceeds.

### Fixed

- **`VERDICT: STOP` costs the FILE its authority, not the SESSION its work.** The courier table has always ended "STOP and say exactly what disagrees, then resume from `docs/PROGRESS.md` instead" — but the phrasing carried in `SKILL.md`, "stops on a `VERDICT: STOP`", says the opposite when read alone, and it is the sentence a session is most likely to meet first. A stale or foreign hand-off is discarded, the session says so in one line, and it resumes from the committed state. Being paralysed by a courier one was free to ignore is not a safety property.
- **The hand-off is a courier and never an authority**, now written wherever it is read: where it and the committed state disagree, `docs/PROGRESS.md` wins and the divergence is stated.

**Reconciliation:** nothing to migrate and no new artifact — this is behaviour, applicable at the next sprint close and the next session start. From the next close on any project, write `docs/continuation-prompt.md` whatever the `Autonomy:` and `Chaining:` lines say, and regenerate it as the work advances rather than leaving it describing a commit that is no longer `HEAD`. **The lock block changed in substance for the second release running** — item 2 gains the read-the-hand-off-first duty and item 5 the sprint-close duty — so `CLAUDE.md` and `AGENTS.md` (and any `GEMINI.md` mirror) need a real content refresh at the next lock-freshness check, not a stamp-only rewrite.

## 5.8.0

Forge issues stop waiting for the next sprint to END. The after-sprint duty guarded one edge of the sprint and left the other open: between two sprints there can be days, and everything that arrived in them — a fresh bug report, or the reply on an `awaiting reporter` issue that decides whether it closes or reopens — sat unread while the new sprint was planned as if none of it existed.

### Added

- **A sprint kickoff sweeps the forge before it plans anything** (Phase 5, "Sprint kickoff", now step 1 — ahead of plan mode and the re-validation). It runs the same inbound sweep the close runs: new issues triaged into `docs/issues.md`, and new comments on existing issues read BY STATUS — on `awaiting reporter` the comment is the verdict (confirms → closed, recorded under `Closed by:`; "still broken" → the work reopens with that report as new evidence), and anything only the user can answer is a stop with its notification, never a guess published on a public thread. **A fresh issue the sweep turns up belongs in the same conversation as what this sprint is about to contain**, not in a note for later — that is the whole point of sweeping before the plan instead of after it.
- **`Last inbound sweep:` in `docs/issues.md`** — one header line, stamped the moment ANY inbound sweep finishes (sprint close or maintenance touch), whether or not it found anything. It is what makes the kickoff check mechanical rather than a recollection of whether someone looked.
- **`Issue sweep interval:` on the project card's `Autonomy:` line** — default 24h, asked once with the after-sprint duty in the session-start setup batch, `n/a` on any project that did not accept the duty. The kickoff compares it against `Last inbound sweep:`: older or missing → sweep now; within the window → say so in one line ("issues last swept Xh ago, within window") and move on. **A sprint chained seconds after a close therefore pays nothing** — the close just wrote the timestamp — which is the only difference between a genuine kickoff and a continuation, and it is decided by data rather than by the session's memory of itself.

### Changed

- The definition of done in `references/project-state.md` now fails a project whose `Last inbound sweep:` is older than its interval while a sprint is open — the same shape as every other state check: verifiable from the files, not from what anyone remembers doing.
- The setup batch's description in `references/phase-1-discovery.md` and `references/adoption.md` names the interval as part of the issue question, so it is asked once with the duty instead of being invented later by whichever session first needs it.

### Fixed

- **`MANIFEST.md` structure**: v5.7.0's Table 3 row had been written into the middle of Table 2, and a stray blank line split Table 3 in two since v5.4.1 — both tables now parse as one table each. Content unchanged in both cases; the manifest is read mechanically after every update, so a broken table is a real defect.

**Reconciliation:** nothing to migrate, no new file, and **the lock block is UNCHANGED** — after two releases that needed a real content refresh, this one is a stamp-only rewrite at the next lock-freshness check. On any project carrying the after-sprint duty: add `Issue sweep interval:` to the card's `Autonomy:` line (24h unless the user says otherwise), add the `Last inbound sweep:` line to `docs/issues.md` (`never` until the first sweep stamps it), and from the next sprint kickoff on, sweep before planning whenever that line is missing or stale. Projects on `issues: on-request` or with no forge are unaffected beyond the `n/a` card value.

## 5.8.1

The chained chat stops deadlocking on the chat that launched it. Under `Chaining: start` the whole mechanism worked exactly as written and produced nothing: the closing session fired the launch while still holding the single lane, the window it opened arrived two seconds later, found the lane held by a PID that was genuinely alive, and stopped. Measured on a real project — not a fork, a deadlock, at link one, with the previous chat's window sitting empty on screen holding a lane it had finished with. No guard misbehaved. The moment named for the release was simply one that never arrives.

### Fixed

- **The lane is released at the CLOSE-OUT, not "on exit" (UNBREAKABLE).** The old rule — "the holder releases it on exit, every exit, including the failing ones" — is unimplementable by the party it names: the holder is a SESSION, and a session does not get to run code when it ends. Its process outlives it; a CLI chat stays alive and idle in its window for as long as the window is open, and under `start` nobody is there to close the window. The release therefore moves to a moment the session can actually act on: the close-out's last act, `scripts/keel-handoff-verify --release`, which frees the lane only if this session is its recorded owner. This is the whole defect: a duty written against the wrong actor reads as satisfied and is never performed.
- **Every close-out releases, not only a chaining one.** `off` and `prefill` are not exempt, and exempting them would be the same error one level down — the user who opens a chat by hand ten seconds later hits precisely the wall `start` hit. The step runs on every path, blocked hand-off included, and is silent and safe on any project that never took a lane.
- **`scripts/keel-continue` hands the lane back IMMEDIATELY BEFORE firing** (contract point 7). The ordering is not a detail: the launched window checks the lane within seconds of opening, so a release that lands afterwards is a race the chain loses — and it loses it looking exactly like the lane working correctly. The script still never TAKES the lane; it gives back what its own session already held, which is the only reading of "the launcher never touches the lock" that leaves the chain able to move.
- **The baton, because a release that depends on the previous session behaving is not a mechanism.** `keel-continue` now writes its own session PID into the launch receipt at the moment it claims it, and the arriving session — verifying the same hand-off, therefore deriving the same receipt identity — compares the live lane holder against it. Holder equals this hand-off's recorded launcher → that holder is by definition a session that already closed out, and the lane passes as a baton rather than stopping the chain. It covers the cases the close-out release cannot: a session interrupted after firing, one that crashed, one still running a `keel-continue` generated before this version. Any other live holder still stops the session, and the check is never loosened into "the holder looks idle" — that would be a guess about another session, where this is the launcher's own statement about itself.
- **A busy-lane `STOP` now names the remedy.** The holder's PID, its start time, and the one thing that frees it: closing that window, or running `scripts/keel-handoff-verify --release` in it. The user is the only party who can clear a lane held by a live session, and the message that told them to stop was giving them a deadlock with no vocabulary for it.

**Reconciliation:** no new file, no card line, and **the lock block is UNCHANGED** — a stamp-only rewrite at the next lock-freshness check. On any project whose card is not `Chaining: off`, the next maintenance touch regenerates both scripts (`keel-continue`: record the PID in the receipt, release before firing; `keel-handoff-verify`: `--release`, the baton, the fuller STOP message) and the close-out gains its final release step. A lane already stuck this way on a project not yet regenerated is cleared by closing the previous chat's window, or by running `scripts/keel-handoff-verify --release` in it.

## 5.9.0

The autonomous cycle stops being interrupted — twice over, by two unrelated mechanisms that produced the same symptom. Once from outside: `auto` mode removes the static-matching problem but routes every command through a classifier, and that classifier reads a comment on a client's issue as an outward-facing action to confirm. Correct default; wrong for this cycle, where replying to the reporter and asking them questions IS the work. Once from inside: a stop written at session scope in a table whose every row describes a single piece of work. Measured on one real project, in one session: the sweep found the issue, built the fix, opened the PR, then stopped to ask permission to tell the reporter about it — and later, with two issues awaiting answers, a merge only the user could perform, and a third issue sitting there fully buildable, reported the blocks correctly, recorded everything correctly, and handed back the afternoon.

### Fixed — the interruption from outside

- **The recommended `.claude/settings.local.json` gains an `allow` block for the forge's conversational surface** (`references/keel-maintenance.md`): reading, commenting, asking, labelling, opening, closing and reopening issues, and merging a PR. Setting `defaultMode: "auto"` was never sufficient on its own and the file said nothing about it, so every project written from this guidance inherited the same interruption. The merge instruction now unions `allow` too, so an existing file catches up without losing a rule the user put there.
- **What is left OUT of that block is part of the fix.** No `gh repo delete`, no `gh release create`, no blanket `gh api`. Publishing a release is a Phase 7 decision the user approves by name; it stays a dialog, and a permission block that quietly swallowed it would be trading the wrong thing for the automatism.
- **The `develop` → `main` boundary is now documented as a rule that needs a mechanism.** `Bash(gh pr merge:*)` is a prefix rule and cannot tell a PR based on `develop` from one based on `main` — the two commands are the same text, and no `ask` or `deny` entry can separate them either, because the target branch is not in the command line. The note that used to end at "which Keel never performs on its own initiative" now says what enforcing it actually takes: a `PreToolUse` hook that resolves the real target (current branch, following any `checkout`/`switch` earlier in the same command line, plus the PR's `baseRefName`) and fails closed when it cannot tell. Keel does not write that hook — it is the user's own machine configuration — but "the assistant simply does not do it" was being offered as a guarantee, and it is not one.

### Fixed — the interruption from inside

Two rules were saying different things and the wrong one was winning, for a structural reason: "Finish the queue; stop only on a real dependency" is written for the moment a block of work ENDS, while "Stopping means: … then wait" is what the assistant meets the instant something blocks MID-FLIGHT. The second is the one in hand at the decisive moment.

- **A stop is scoped to the ITEM, never to the SESSION (UNBREAKABLE)** (`SKILL.md`, "When to stop and ask"). Every row of that table says one piece of work cannot proceed on the assistant's own judgment; none says there is nothing else to do. So the stop parks that item — question asked, notification sent, state recorded — and the session moves to the next thing in the queue that does not depend on the answer. Waiting is correct only when nothing independent remains, and that is established by looking, not assumed because something is blocked. Several parked items are listed together so the user answers them in one pass instead of being made the bottleneck of each in turn.
- **"Finish the queue" now says it holds mid-block, not only at the end of one.** The rule listed the two reasons Keel stops; it now says that *every* remaining step must depend on the missing thing, and names the reading that was being lost — "the thing I was doing got blocked" is a reason to switch items, never a reason to stop.
- **`Handover: blocked` describes the SESSION, not an item in it** (`references/project-state.md`). Chaining fired only on a clean hand-off, and any "When to stop and ask" row wrote `blocked` — so one parked question cost the entire next session: nothing was opened, and the user returned to a chain stopped at a link that had somewhere to go. A hand-off with parked items and buildable work left is `clean` and CARRIES the parked list as open items, so nothing is lost by not stopping. Genuinely blocked still means blocked, and still never chains.

### Fixed — the language of the forge

The language contract covered two cases, "everything Keel creates" and "the conversation with the user", and a forge issue is neither. Read as the first — which is the reading the wording invites — it answers a Spanish bug report in English.

- **An issue Keel OPENS is always English**, title and body, whatever language the conversation runs in: a public, permanent, indexed artifact of the project, read by contributors who were never in the conversation.
- **A reply to an issue somebody else opened follows THAT issue's language**, read from the reporter's own text — never from the repository, never from the conversation, never guessed from a name, a locale or a timezone. Mixed thread → the language the reporter last used; genuinely undecidable → English. This is the half the English default gets wrong, and the cost of getting it wrong lands on the person who did the project the favour of reporting the bug, on their own thread. Recorded in both places the messages are actually written: `SKILL.md` "Token economy" and the three-beat lifecycle in `references/project-state.md`. The orthography contract holds in whatever language it lands in — a reply in Spanish carries every accent and every ñ.

### Added — issue capture, asked and never assumed

A defect the user reports in conversation is worked and then disappears: what was wrong, what it turned out to be and how it was fixed live in a chat log and nowhere a person can search in six months.

- **New setup question (2b) and new card value `Issue capture: on|off|n/a no forge`.** With `on`, a problem the user reports becomes a forge issue, and the issue is **opened BEFORE the work starts** — that ordering is the point, because a session that dies mid-fix, runs out of context or is interrupted then leaves the report standing on the forge rather than only in the chat. Keel comments as the work advances (what it turned out to be, the commit or PR, anything that changed the diagnosis), not only at the end.
- **It is ASKED, never assumed.** A tracker is a shared public surface, and a project that keeps its tracker for third-party reports is entitled to that; filling it with entries nobody asked for is not a favour. The question is only put where the project has a forge.
- **A duplicate is a comment, not a second issue** — if an open issue already covers it, the information goes there. And the user still closes it: "Keel never closes an issue on its own reading of the code" holds unchanged, and the reporter being the person in the chat does not soften it.

**Reconciliation:** nothing to migrate, no new file, and **the lock block is UNCHANGED** — a stamp-only rewrite at the next lock-freshness check. **One new card value:** ask Question 2b once on every existing project that has a forge and record `Issue capture:` on the `Autonomy:` line — a project with no forge records `n/a no forge` and nothing changes for it. Then, where it applies: on any project whose `.claude/settings.local.json` Keel wrote, the next maintenance touch merges the new `allow` block into it (union, never overwrite, never dropping a rule the user put there) and says so in one line. Projects with no forge, or answering `no` to the autonomy question, are unaffected — no file was written for them and none is now. The stop-scope rule needs no action at all: it lives in `SKILL.md`, which the lock's item 1 already requires reading in full every session, so every project picks it up the moment its copy is current, from the next session on.

## 5.10.3

### Fixed — the `scripts/keel-continue` contract closes four gaps found on a real macOS `start` launch

A project chaining via `Chaining: start` fired three broken launches in a row before a working one, each masking the next, and `osascript` reported success in every single attempt — the exit code proved a window opened, never that the intended command ran inside it. A fourth, unrelated bug then made the script's own live `command -v claude` re-check (v5.10.2, point 5a) report "not on PATH" on the exact machine that was running Claude Code to produce that message. None of the four is project-specific: they are properties of `osascript`/Terminal.app/BSD `mktemp`/`claude`'s own argument parser/the native installer's install location, so any project generating this script fresh, on any machine, could hit the same four bugs independently.

- **New contract point 6a — the Terminal command is never an interpolated string.** It must be written to a real, executable script file (shebang + `chmod +x`) and run BY PATH — a bare path needs no nested quoting across the three layers (`osascript`'s generating shell, the AppleScript string literal, the shell Terminal spawns), which do not compose safely when interpolated and fail *silently*: the window opens and receives the literal, un-executed text instead of running the command. The point also names a `mktemp` trap the fix for 6a predictably reaches for: a template with a literal suffix after the `X` run (`...XXXXXX.sh`) is not randomized by BSD/macOS `mktemp`, so the first call succeeds and the *second* collides with the file the first one left and fails — a trap a single test run will not catch.
- **New contract point 6b — the hand-off's raw content is never passed as `claude`'s CLI argument.** `docs/continuation-prompt.md` is specified to open with a `---` freshness header, and `claude`'s own argument parser reads a leading `---` as an unrecognized option and exits, regardless of how correctly the argument was quoted at the shell level — the failure is inside the target program's own parser, downstream of every shell-level quoting layer. The fix is a short instruction telling `claude` to read the file itself, which also never starts with `-`.
- **Point 8 now states the exit-code trap explicitly:** a `start` action's own exit code proves a window opened, not that the intended command ran inside it — verify by reading back the new window's actual terminal history (macOS: `tell application "Terminal" to get history of tab …`) while developing or changing the script, since that is the only way to distinguish "launched" from "launched something broken that also exits 0."
- **The canonical `env.PATH` template (`references/keel-maintenance.md`, "Permission mode") now always includes the user's own per-user installer directory.** Claude Code's native (non-npm) installer places its binary at `~/.local/share/claude/versions/<version>`, symlinked from `~/.local/bin/claude` — a per-user location the MacPorts/Homebrew/system-oriented template cannot contain by construction. Its absence is not cosmetic: it makes `scripts/keel-continue`'s own live PATH re-check produce the single most misleading symptom available — "tool not installed," stated with apparent authority, on the machine actively running it. The template's example value is written with the directory resolved to its literal absolute path, per the existing "never `$HOME`, never any variable" rule.

Recorded in `keel/references/project-state.md` (the `scripts/keel-continue` contract, new points 6a/6b and the point 8 addition) and `keel/references/keel-maintenance.md` ("Permission mode").

**Reconciliation:** nothing to migrate, no new file, no card line, and the lock block is unchanged in substance — a stamp-only rewrite at the next lock-freshness check. No per-project action: the rules live in files every session reads in full, so a project regenerates a conforming `scripts/keel-continue` at its next scaffold touch and fixes its own `.claude/settings.local.json` `env.PATH` the same way, in one line, the next time that file is touched.

## 5.11.0

### Added — the test-first policy: WHEN a test is written, settled once per project

Keel already fixed who drives a test and what evidence it leaves; it never said when the test is written relative to the code. In practice that meant after, and a test written after the implementation is written by someone who already knows how the implementation works: it describes what the code does rather than what was asked for. Where those two differ — the only case worth catching — the difference is invisible, because it is present in both the code and the test. The suite goes green, stays green, and the defect is now protected by a passing test everyone reads, correctly, as evidence. Driving the test does not help: a driven test that asserts the wrong thing is driven, recorded, reproducible and wrong.

The answer is deliberately a policy and not a doctrine. Where test-first is cheap it is mandatory, where it is expensive it is opt-in per project, and where it is counterproductive it is forbidden outright.

- **New project-card line `Test-first policy:`, asked ONCE at Phase 2 §4e** with three values. `pure-logic` (the default for new projects): anything that is a pure function of its inputs — signature computation, parsers, serializers, validators, state machines, money arithmetic, entitlement and expiry resolution — gets its test written and seen failing BEFORE its implementation. `pure-logic + acceptance`: each slice additionally opens by turning its `AC-nn` into one executable check that fails, and is built until that check passes; scopable to part of the codebase, recorded in the technical plan. `none`: neither applies, and it takes its own `docs/decisions.md` entry — the default is never dropped by omission.
- **An explicit not-applied list, which is as much of the policy as the mandatory half:** UI markup and layout, framework glue and bootstrapping, exploratory integration with a third party whose real behaviour is not yet known, and one-line configuration. Coverage there still comes from the driven tests, the playground and the static checks; only the ORDER changes, and only where it buys something. A rule with no boundary gets applied where it does damage and then abandoned entirely.
- **The spike escape hatch, with its closing condition.** When a third party's real shape is unknown, writing the test first is writing fiction: spike against the real thing, then pin the behaviour with a test the MOMENT the shape is known and delete or rewrite the spike behind it. A spike that quietly becomes the implementation, with its test written afterwards from the code it produced, is this whole section's failure arriving through the one door left open for it.
- **Two rules that hold at EVERY value, including `none`.** (1) **Every bug fix starts from a failing reproduction test** — slice, maintenance and hotfix alike. Keel already required a regression test; the order is what changes, and it is not cosmetic: a test written after the fix demonstrates that the code does what the code does, never reproduced the bug, and so proves nothing about the bug's return, which is its only job. This is the rule most likely to be traded against urgency and the one whose absence surfaces three versions later as the same report from the same customer. (2) **A test derived from an `AC-nn` or a reproduced bug is NEVER edited to make it pass** — if the test is wrong the requirement is wrong, and that is a `docs/decisions.md` entry or a Design Request, never an assertion quietly relaxed to reach green. The boundary is precise and it is about the assertion: renaming, moving, improving the failure message and fixing the test's own scaffolding are outside the rule; changing the set of behaviours that would pass it is inside it.
- **The red is observed, and for the right reason.** Run the test and watch it fail; confirm the message names the ABSENT BEHAVIOUR and not a broken import, a missing fixture or a typo'd path — a red for the wrong reason is a green in waiting, and it produces a test that could never have failed, counted in coverage forever with nothing underneath it.
- **New `Red first` column in `docs/05-test-points.md`**, a closed enum of five values like `Coverage` before it: `observed` (the failure line is in the evidence cell), `n/a — policy`, `n/a — out of scope`, `n/a — predates` (the row is older than the project's adoption of the policy — it is never retroactive) and `n/a — delegated` (the row's `Coverage` is one of the eight tags).
- **Three `scripts/keel-verify` behaviours, asymmetric on purpose.** It FAILS an empty or unrecognized `Red first` cell — a script can only count what it can recognise. It FAILS a row claiming `observed` with no failure output in its evidence cell — a claim without its evidence. And it REPORTS, never fails, every row that is neither `observed` nor `n/a — delegated`, at the sprint close: no script can decide whether a given piece of code is pure logic, so every value carrying that judgment has to be visible, or the mildest one quietly becomes the default. On a `none` project the report is one line naming the policy and its decision entry.
- **The adoption batch asks the question too** (`references/adoption.md` step 3) — an adopted project never passes through Phase 2, and would otherwise carry a card line the self-audit and the definition of done both require it to have.
- **New eval scenario, `tests/evals/scenarios.md` E8:** the red distinguished from a setup failure and recorded, plus two negative checks — the assertion widened to reach green (fails the scenario outright, however green the suite ends up) and a regression test written after its fix.
- **Two new anti-patterns: 12c "The test edited until it passed"** (the trap test-first makes MORE likely, because the test is newest and least defended exactly when it is doing its most valuable work) and **12d "The test that could never have failed"** (the only trap in the catalogue that produces no symptom at all). Self-audit questions 15 and 16.

Recorded in `keel/references/test-automation.md` (new section "When the test is written — the test-first policy" and four definition-of-done lines), `keel/MANIFEST.md` (Table 1's test-point row, the project-card line list, Table 3's v5.11.0 action), `keel/references/adoption.md` (the question in the adoption batch), `keel/references/phase-2-functional-spec.md` (new step 4e, the plan's `## Testing` line, definition of done), `keel/references/phase-5-development.md` (the slice's first bullet, the reproduction-first bug rule, the `keel-verify` check, the test-point table and its format rule, definition of done), `keel/references/maintenance.md` (hotfix step 2, the full-suite rule, definition of done), `keel/references/anti-patterns.md` (12c, 12d, self-audit 15/16), `keel/references/project-state.md` (the card line), `keel/SKILL.md` (new principle and the cross-cutting section) and `tests/evals/scenarios.md` (E8).

**Reconciliation:** one new card line and one new test-point column, both cheap and both applicable at the next natural touch; no migration and no new file. The lock block is unchanged in substance — a stamp-only rewrite at the next lock-freshness check. See Table 3 of `MANIFEST.md`.

## 5.12.0

### Added — art direction: the step where inventing is the work

Keel is built against drift. Never invent silently, code adapts to the design, divergence is a Design Request and never a creative choice. That discipline is correct everywhere except at the one point where inventing IS the job, and there it had nothing to offer: the brief asked for the aesthetic in one or two lines of tone, and a process with no answer at that step returns the model's default. The result is not a bad design. It is a competent design that looks like the previous one, and like a large fraction of everything else built by an assistant that year.

Three causes compound, and none of them is a mistake anyone made:

- **The aesthetic was requested in adjectives.** "Technical and sober", "minimal and editorial", "bold". An adjective is a pointer to the average of everything it has ever described, so a brief built on adjectives returns the average by construction. No amount of additional adjectives escapes it; they narrow toward a mean, they do not generate.
- **Nothing was forbidden.** Keel asked the USER for vetoes at discovery and contributed none of its own. A model with no blacklist reaches for the patterns most represented in its training data, which are precisely the patterns readers have learned to recognise as machine-made.
- **Nothing remembered the previous site.** Keel has project memory (`PROGRESS.md`, `decisions.md`, `lessons-learned.md`) and class memory (`anti-patterns.md`); it had no memory ACROSS projects. Two similar briefs MUST produce the same site, because nothing in the system knows the other one exists. This is the cause that produces the complaint as it is actually voiced: they all look too similar.

The answer is not to loosen the anti-drift discipline, which is what makes Keel work. It is to open ONE bounded, rule-governed step where invention is mandatory, close it with a recorded decision, and let the normal regime resume unchanged. Everything below is website-scoped (Phase 8) and applies from the next site or the next redesign onward.

- **New reference `references/phase-8-art-direction.md`, run BEFORE the design brief** — after the section catalogue, before `phase-8-design-direction.md` is filled in. Eight steps with their own definition of done, checked item by item like every other Keel gate, so skipping it leaves a visible ✗ rather than a silent omission.
- **The Design Read, declared in one sentence** naming site type, audience, archetype and the aesthetic family being leaned toward. It is the record that a reading happened instead of a default firing. A read that could be pasted onto another project has not been done. Five archetypes are named, including the one Keel actually builds most and which no external design skill covers: the technical product catalogue, where buyers compare before they buy and density and evidence beat atmosphere.
- **Four dials, each set with its one-line reason.** `LAYOUT_VARIANCE` and `VISUAL_DENSITY` and `MOTION_INTENSITY` bounded by the vanilla rule (CSS transitions, CSS animations, scroll-driven animations, `IntersectionObserver`; above 3, `prefers-reduced-motion` is specified per animated element and not added later). The fourth is Keel's own and has no counterpart anywhere: **`EVIDENCE_RATIO`**, the proportion of the page that is real and checkable — screenshots, prices, versions, real code, concrete counts — against decoration and atmosphere. A technical audience discounts a site in proportion to how much of it is unfalsifiable, which is the specific way a credible catalogue and a landing page differ. Presets per archetype exist to be argued with; a dial silently left at its preset is not set, because the reason is what makes it arguable later.
- **The divergence round, which is the engine.** Before the full brief, Design produces THREE directions for ONE section — the hero, or the product card, or the docs index by archetype. Each belongs to a differently NAMED aesthetic family (three variations on one family is one direction shown three times, and it is the most common way this step is performed without being done); at least one is a deliberate risk that could be rejected outright, because a safe-safe-safe triad reaches the average by a longer route; each carries its tokens and a one-sentence fit rationale, since a direction without tokens is a picture. The user picks one or consolidates two. **The choice is recorded in `docs/decisions.md` with the rejected alternatives named, and that closes the subject** — from there the normal regime resumes and later divergence is a Design Request. Cost, stated plainly: one extra Design round on one section, which is the cheapest place to spend it and in practice the only step that reliably produces something original. It is not skippable for time; a waiver is its own decision entry naming what was traded away.
- **Signature elements.** One or two treatments that recur across the whole site and belong to this project alone — a border behaviour, the way a screenshot meets its frame, a table row's anatomy, a single typographic move used consistently and nowhere else. Not the palette and not the typeface, which are inheritance-level decisions. This exists because **avoiding what is wrong is not the same operation as having something of your own**: a page can pass every blacklist item, hit every dial and still be forgettable. Each element is declared with its recurrence points and CSS treatment, and the Phase 4 gate fails one that is named and absent from the delivered CSS.
- **New machine-local anti-repetition ledger at `~/.keel/art-ledger.md`** — outside every repository by construction, since its whole job is to span projects; never committed, never shipped with the skill. The last three entries are a live constraint on the next site: primary typeface and pairing, palette family and accent hue, hero paradigm, grid family and every signature element are unavailable. Missing or unparsable is an absent constraint stated in one line, never a block, never reconstructed from memory. When the constraint genuinely cannot be honoured — an inherited brand typeface, an archetype narrow enough that the last three used the only sane hero — say what could not be varied and why, and vary something else; a forced-bad decision taken to satisfy the ledger defeats its purpose, and the only thing never acceptable is repeating silently. **The entry is appended by the assistant at the close, from the direction actually chosen**, because a ledger somebody has to remember to update promises a guarantee it does not deliver, which is worse than having none.
- **A literal blacklist, in vanilla CSS terms**, across layout, type, colour and material, content and punctuation. Literal is the point: "avoid generic layouts" cannot be checked and therefore is not a rule, while "no three equal feature cards in a row", "not `#000000`", "not the cream-plus-brass-plus-oxblood palette as the reflex for anything premium", "no more than two consecutive sections sharing a layout family", "no fake product UI built from styled `div` elements" all can be. Every item is a default overridable by an explicit recorded user decision, never by the assistant deciding a project is the exception.
- **The em-dash rule, binary and greppable.** `—` and the separator `–` are forbidden in every string visible on the BUILT SITE: headlines, eyebrows, labels, buttons, body copy, quotes and attributions, captions, alt text, meta descriptions and structured-data strings. Ranges use a hyphen. The scope is the rendered site only — Keel's own `docs/`, the briefs and this changelog are untouched — and the reason is narrow and empirical: the em-dash is the single most reliable textual signal that a page's copy was machine-written, and on a site whose credibility rests on being made by a person that signal costs more than the punctuation is worth. One visible occurrence fails the check.
- **The self-critique pass**, two questions answered in writing: which parts of this are the default any assistant would have produced from this brief, and which specific thing makes this site this site rather than the archetype. Two questions and not another checklist, because the failure it catches is judgment-shaped — the site that ticks every box and has nothing of its own. An answer to the second that would read identically pasted into another project has not answered it.
- **New conditional handoff artifact `SPEC/art-direction.md`**, joining `screenshots.md` as the second website-only addition to the contract. It carries the read, the dials with reasons, the chosen direction with its rejected alternatives and its decision entry, every signature element with its recurrence points and CSS treatment, blacklist overrides, and both self-critique answers. It is a contract artifact and not a note: the Phase 4 completeness gate fails a website handoff without it.
- **`phase-8-design-direction.md` §2 no longer asks for tone in adjectives.** It carries the recorded art-direction output verbatim instead, and says why the old question was the mechanism producing the problem rather than the one solving it. `design-brief-template.md` gains §2b for the same content, skipped by non-website projects.
- **Two verification points, so the gate is not only at the front.** The launch checklist verifies on the live site that every signature element is present and recurs where the SPEC says, that the dial values are recognisable in what shipped (a site specced at `EVIDENCE_RATIO` 9 with no real screenshots or figures failed the direction regardless of how it looks), that the blacklist holds, that the em-dash grep returns zero, and that the ledger entry is WRITTEN rather than promised. And **new anti-pattern 24, "The site that looks like the last one"**, with self-audit question 24, carries the same check into every sprint close, Phase 7 gate and adoption.

**Attribution.** The Design Read, the numeric dials, the literal-blacklist approach and the pre-flight-as-gate are adapted from `taste-skill` by Leonxlnx (MIT), and adapted is the operative word: that skill targets React, Next.js, Tailwind and Motion and prescribes npm design-system packages, all of which Phase 8's vanilla rule forbids, so nothing framework-bound survives the adaptation. The divergence round, the signature element, the `EVIDENCE_RATIO` dial and the anti-repetition ledger are Keel's own and have no counterpart there. Keel deliberately does NOT depend on that skill or recommend installing it: a recommendation is the weakest gate available, it would put a second and contradicting authority next to Phase 8's own rules, and Phase 8 exists in its current form precisely because the standalone `keel-web` skill was absorbed to remove cross-skill dependency.

Recorded in `keel/references/phase-8-art-direction.md` (new), `keel/references/phase-8-website.md` (core stance, steps table, run order, definition of done), `keel/references/phase-8-design-direction.md` (the run-first pointer, §2 replaced, definition of done), `keel/references/design-brief-template.md` (§2b), `keel/references/handoff-contract.md` (the two website `SPEC/` files, completeness), `keel/references/phase-8-launch-checklist.md` (the live verification and its definition of done), `keel/references/anti-patterns.md` (trap 24, self-audit 24), `keel/SKILL.md` (phase table, reference index) and `keel/MANIFEST.md` (Table 1's two rows, Table 2, Table 3's v5.12.0 action).

**Reconciliation:** one new reference, one new conditional handoff artifact, one machine-local file. No migration, no card line, and the lock block is unchanged in substance — a stamp-only rewrite at the next lock-freshness check. Website projects only, and not retroactive: no site already built is revisited, and the ledger starts empty, which for the first site after the update means no constraint and a written entry at its close. ## 5.13.0

### Added — `scripts/keel-chain-check`: the unattended chain stops being a contract nobody executes

Keel's own rule is that a check which cannot be run is a promise, and that this skill does not write promises as checks. Chaining was the one place that rule was never applied to itself. The launcher carried a thirteen-entry numbered contract; `start` carried four gates; the permission mode, the `env.PATH`, the two allow-list entries and the single lane each carried their own rule — and every one of them was prose. Nothing executed any of it. The first thing that ever checked whether a project could actually chain was a real close-out: end of session, context nearly spent, nobody watching.

That is what produced the field failure pattern, and the pattern is more revealing than any individual bug. The chain did not break in novel ways. It broke because a piece of the contract had been silently unmet for days — the script was never generated, or it was generated before v5.10.3 and carries one of the four launch bugs, or its allow-list entry is missing, or `permissions.defaultMode` is `manual`, or `env.PATH` hides `claude` from its own detector — and the mechanism reported it exactly once, at the moment nothing could be done about it. **The failure was never that the chain broke. It was that it broke where it could not be fixed.**

- **`scripts/keel-chain-check`, generated at the Phase 5 scaffold on any project whose card is not `Chaining: off`, with one allow-list entry (`Bash(./scripts/keel-chain-check:*)`).** It writes nothing, changes nothing and asks nothing. Twelve structural rows, one line each, plus `VERDICT: READY | NOT READY | N/A (Chaining: off)` and a `--json` mode. Section A runs everywhere: the card parses, `scripts/keel-continue` and `scripts/keel-handoff-verify` exist and are executable, both allow-list entries are present in every capable tool's container, `permissions.defaultMode` is `auto` on an automatic card, `env.PATH` is expanded and absolute and carries the system directories and the per-user installer directory, and `docs/continuation-prompt.md` is gitignored. Section B adds the `start`-only rows: `claude` resolves live **under the DECLARED `env.PATH`, not merely under the current shell's** — two different questions, and only the second matches what the chain will actually experience; the lane directory is reachable and writable; the four measured v5.10.3 launch bugs are absent from the launcher, by grep, because each is a greppable property rather than a judgment; the launcher passes an explicit `--model` and the card carries a real `Chaining model:` behind it; and the proof has not gone stale.
- **`--smoke`, and it is the only thing in Keel that proves the launch RUNS.** Contract point 8 is true and unfixable by reading: a `start` action's exit code proves a window opened, never that the intended command ran inside it — all four bugs of the v5.10.3 incident exited 0. So the smoke test fires the recorded action for real, with a harmless nonce prompt that is not the hand-off, in a dedicated receipt namespace that never touches the real hand-off, never takes the lane and never counts against the circuit breaker (a test that consumes the mechanism it tests is worse than no test); **reads the new window's own terminal history back** and asserts the nonce arrived; then closes the window it opened. Where no read-back is available the result is `INCONCLUSIVE` — a third state, reported as such, never quietly promoted to passing.
- **New card line `Chain verified:`** — date, tier proven, Keel version, and the checksum of `scripts/keel-continue` at the moment the launch was observed to work. Written only by `--smoke`, never by hand and never from a reading of the script. This is the load-bearing piece and the reason the whole thing holds: every other row proves the parts are present and correctly shaped, and only this row answers whether the launcher has ever been *observed* to work — a question that any edit to the launcher re-opens automatically. **A launcher that changed since it was last proven is an unproven launcher**, however careful the change looked, and nobody has to remember that.
- **`--smoke` is mandatory at exactly three moments, and the list is exhaustive:** at the Phase 5 scaffold, the moment the launcher is generated (a launcher that has never launched is not installed, it is merely present — the rule this scaffold already applies to the test drivers); whenever `scripts/keel-continue` is regenerated or edited, by anyone, for any reason; and whenever `Chaining:` is raised a tier, because the tiers do not share a command and a proven `prefill` says nothing about `start`. It is deliberately NOT run at every sprint close: the close runs the static rows, which are instant, and the window-opening proof is checkpointed by checksum rather than repeated — a smoke test on every close would open an extra window at exactly the moment the user is trying to walk away.

### Added — the chained chat launches on a model somebody chose

A new `claude` process inherits nothing from the one that launched it. Keel has known half of that since v5.5.2, when the registry's claim that the CLI "inherits `cwd`" turned out to be false of the action actually verified for `start` — `osascript` asking Terminal.app to `do script` opens a new login shell, which starts in `$HOME`. The other half went unnoticed for exactly the same reason the first half was reassuring: nothing complains.

Claude Code resolves the model as `/model` in-session, then `--model` at startup, then `ANTHROPIC_MODEL`, then the `model` field in settings — and the flag and the variable **apply only to the session launched with them**. A fresh process runs that order from scratch. So a chain fired from an Opus session with a bare `claude '<prompt>'` comes up on whatever the settings file resolves to. Measured, repeatedly: every link on Sonnet while the session launching it was on Opus. Nothing failed. The work got done, at a capability and a price nobody agreed to, and the only way to notice was to look at the model indicator in a window you were not watching — which is the whole premise of `start`. (Resumed sessions are the exception that proves the rule: `--resume` and `--continue` restore the model from the transcript, and a chain is not a resume.)

- **New card line `Chaining model:`**, asked at Phase 1 step 0a in the same breath as `Chaining:` and only when the answer is not `off`. The model in use in the asking session is proposed as the value; the user confirms or changes it, and that value is used at every link until they change the card. It is a real question and never a silent default, because getting it wrong costs money in a direction nobody is watching.
- **New contract point 5b:** `scripts/keel-continue` passes `--model <the card's value>` on every `start` fire. The card line missing or `n/a` on a chaining project means print and name the absent line, never fire a launch whose model is a guess. **And never substitute the launching session's model for the card's value** — the card is a recorded decision; the session's model is an accident of how the user happened to start it.
- **The registry row and every prose copy of the command now carry the flag:** `cd '<absolute repo root>' && claude --model '<Chaining model:>' '<prompt>'`. The `cd` and the `--model` are the same rule applied to two different things a new process does not inherit.
- **Row 10a in `keel-chain-check`** catches both halves by grep: the launcher builds its invocation with an explicit `--model`, and the card carries a real value behind it. Either missing is `NOT READY`.

### Added — `Mode:` in the hand-off freshness header

The most common chaining failure does not look like a chaining failure at all. The chain fires perfectly. The window opens perfectly. The arriving session reads the hand-off, begins work in `manual` because nobody told it otherwise, and stops on the first composite command at a permission dialog nobody is there to answer. From outside, that is indistinguishable from a chain that never fired, which is why it is so consistently misdiagnosed as one.

The continuation template's step 1 already said to apply the card's `Autonomy:` and `Notify:` — but it said it about a card the session had not read yet, three steps before it reads one. So the header now carries `Mode:` (the card's `Autonomy:` and `Chaining:` values) and the arriving session applies it first. It is carried, not checked: the card remains the authority and a disagreement is stated in one line and resolved in the card's favour — but a hand-off that never mentions the mode cannot even produce the disagreement.

### Changed — where the check runs, and what it is allowed to do

- **Two run points.** At every session start on a chaining project, in the fixed reading order beside `scripts/keel-doctor --check` — a `NOT READY` at the START of a session is a problem with hours left in which to fix it. And immediately before the close-out fire, so the person learns which row broke instead of finding a printed prompt and no explanation; in automatic mode the failing rows also go out through the recorded notification channel.
- **`keel-chain-check` never vetoes a fire, and this is deliberate.** A `NOT READY` does not stop the close and does not stop the launch: the close-out still runs `scripts/keel-continue`, which still decides for itself, exactly as before. Adding a fifth entry to the closed list of four things that may stop a chain would hand the session back the judgment call v5.10.2 removed, at the same moment and under the same conditions that produced the original incident. It is a diagnostic. It explains what happens; it never decides it.
- **The rows come from the same source as the contract** — one row per numbered `keel-continue` point and per `start` gate — so a requirement added to `references/project-state.md` without a corresponding row is a release bug, in the same way a manifest row missing its reference is. `scripts/keel-verify` checks that the script exists and that its row count matches.
- **Phase 5's definition of done gains one row:** on a chaining project, `scripts/keel-chain-check` exists, is committed, reports `READY`, and the card's `Chain verified:` checksum matches the launcher on disk.

# DECISIONS — Keel (the skill itself)

> Append-only. One entry per decision. Never re-litigated by the assistant on its own initiative;
> an explicit later instruction from the user supersedes an entry and is recorded as a new one.

## D-001 — This repository keeps living state, and it is a maintenance project

- Date: 2026-07-30
- Context: The repository that authors Keel had no `docs/PROGRESS.md` and no `docs/decisions.md` — the two files Keel requires of every project it manages. Sessions working on the skill re-derived its position from git history and from whatever the user remembered.
- Decision: Create both files and run this repository in Keel's **maintenance** mode rather than as a greenfield project. Phases 1–4 are recorded `n/a`: the skill exists, is released and has an installed base, so a discovery phase would be fiction. Each version is a change set gated by `python3 tests/lint-release.py`.
- Alternatives considered: (a) a full adoption pass producing `docs/01/02/03` as-built — rejected: for a Markdown instruction set, `SKILL.md` and `MANIFEST.md` already ARE the spec and the parity list, and reconstructing them into as-built docs would create a second source of truth that immediately drifts. (b) Leaving the repo stateless — rejected: the skill that makes state mandatory cannot be the one project without it.
- Consequence: The state files are maintained at the moment of change, like any Keel project. `Keel baseline:` always equals the version being authored, because this repo writes the version it runs.

## D-002 — `develop` integrates; `main` is the user's

- Date: 2026-07-30
- Context: Recorded here as the project-level instance of the git-flow rule introduced skill-side in v5.5.0 (SKILL.md, "Git flow").
- Decision: Work branches start from `develop`. The assistant merges work branches into `develop` and pushes, **without asking**. The assistant **never** merges `develop` into `main`, never tags, and never publishes a release on its own initiative — those are the user's acts, performed only on an explicit instruction in the conversation.
- Alternatives considered: committing straight to `main` — rejected: the skill has an installed base that pulls from tags, so `main` moving unreviewed would ship unreviewed instruction changes to real projects.
- Consequence: Control over what reaches users sits at the `develop` → `main` merge, not at the push. When `develop` holds work ready for release, PROGRESS.md says so under "Ready for `main`" and the assistant stops there.

## D-003 — Pushing is the assistant's job, not the user's

- Date: 2026-07-30
- Context: Work was accumulating as local commits waiting for a human to push them, which is a queue nobody owns: the user has to remember, and a session that ends leaves work invisible to every other checkout.
- Decision: The assistant pushes its own work. No commit is left local "for the human to review and push". Review happens at the `develop` → `main` merge (D-002), not by withholding a push.
- Consequence: `Autonomy:` on the project card records **automatic**, which is what makes pushing the assistant's duty here (D-004). Consequently `Bash(git push *)` is NOT in the `ask` list of `.claude/settings.local.json` — an earlier draft of v5.5.0 put it there and it was removed as directly contradicting this decision.

## D-004 — Automatic mode is the user's question; the file that implements it is not

- Date: 2026-07-30
- Context: v5.5.0 went through two reversals here. It was first drafted with the permission mode as a question; a relayed instruction then said Keel should write `.claude/settings.local.json` on its own initiative without asking; the user finally settled it: **the person defines the mode when asked, and everything else hangs off that answer.**
- Decision: The setup batch asks **three** questions, and automatic mode is the first because it is the hinge. Answer yes → Keel writes or merges that file itself and announces it in one line (the MODE was the question; the file implementing it is not a second one), asks nothing further, and performs every merge to the integration branch and every push. Answer no → no file is written, Keel asks every time and pushes only what was explicitly requested. Merging never removes or reorders a rule the user put there, and the committed `.claude/settings.json` is unaffected — it still requires explicit confirmation.
- Consequence: Three questions — automatic mode, forge-issue duty, notification channel — recorded on `Autonomy:` and `Notify:` and never re-asked. The regime is read from the card, never inferred per action. This entry supersedes both earlier drafts, per the rule that a later explicit instruction wins.

## D-005 — Out-of-band notification is protocol-first, and this machine has no channel

- Date: 2026-07-30
- Context: v5.5.0 adds `references/notifications.md` so a blocked session reaches the developer. The intended channel was email through the Gmail connector.
- Decision: Define the protocol around **delivery**, not around a specific vendor: a channel counts only if it actually delivers, the capability is probed every session, and a connector that can compose but not send is recorded as compose-only. The measured fact behind this: the available Gmail connector exposes draft creation, reading and labelling, and **no send operation** — so a draft would have been recorded as a notification while alerting nobody.
- Consequence: The protocol is vendor-neutral and probe-first. See D-007 for the channel actually adopted.

## D-007 — The native harness notification is the default channel

- Date: 2026-07-30
- Context: D-005 left this repository with no channel, on the assumption that email was the route. The harness's own notification tool turned out to be available, and it needs no address, no credential, no server and no setup.
- Decision: Adopt the environment's native notification as the default channel, here and as the first-preference tier in `references/notifications.md`. Build nothing until it proves insufficient.
- Alternatives considered: an SMTP sender via a Google app password (`msmtp` or a small script) — deferred, not rejected: it is the correct escalation for absences the native channel cannot reach. A self-hosted Gmail MCP with a send scope — rejected as more ceremony than the SMTP path for the same result.
- Consequence: Two properties are recorded because both are easy to misread. **Reach:** desktop always, phone only while Remote Control is connected — so it covers "walked away from the desk" and not "out of the building". **Suppression:** it deliberately does not fire while the user is at the terminal and reports "not sent"; that is the anti-noise policy one layer down, so it counts as delivered-or-redundant and is never escalated to another channel or reported as a failure. Untested so far: the only honest test is one fired while the user is genuinely away, which has not happened yet.

## D-008 — Fan-out workers run under `auto`; `bypassPermissions` is never used again

- Date: 2026-07-30
- Context: Raised by a review that spotted v5.5.0 contradicting itself — the session-start step writes a `deny` block and the fan-out dispatched workers with `--permission-mode bypassPermissions`, which evaluates no rules at all. The user then supplied the decisive fact from practice: **`bypassPermissions` asks for confirmation every time**, so the premise it was chosen on ("it is what lets an unattended worker finish") was simply wrong.
- Decision: The dispatch uses `--permission-mode auto`, permanently. Recorded UNBREAKABLE in `references/project-state.md`. If workers stall on an action the allow-list does not cover, the fix is to extend the allow-list — never to bypass.
- Alternatives considered: keeping `bypassPermissions` and relying on the fan-out's other three preconditions (a person in the dispatching session, slices approved at the kickoff, worktrees of this repository) — rejected twice over: those were never a substitute for permission evaluation, and the flag does not even deliver the unattended run it was picked for.
- Consequence: `auto` is not a drop-in — a worker in `-p` mode cannot be asked, so an uncovered action is refused and the slice may fail. That is the correct failure direction: a refusal surfaces in the worker's report; an unattended `sudo` surfaces nowhere. A second hole found while verifying this one: `.claude/settings.local.json` is gitignored, so a worktree checkout does not carry it and the worker would fall back to user-level config regardless of the flag — the dispatch now copies it in before launching.

## D-009 — The launch is the script's job, and a fired launch is spent

- Date: 2026-07-30
- Context: The user showed a real close-out from another project (still on an older Keel) that opened five terminal windows and killed four of them by hand. Reading v5.5.1 against that transcript found the skill genuinely at fault in four places, not merely un-upgraded: nothing forbade a session from composing the launch itself when `scripts/keel-continue` was absent; the tool registry claimed the CLI "inherits `cwd`", which is false of the `osascript`+Terminal.app action it declares verified for `start`, since `do script` opens a login shell in `$HOME`; the never-retry rule was worded for "I cannot tell whether it opened" and so was read as permitting kill-and-relaunch when the window had opened wrong; and `phase-5-development.md` described the generated script as firing a URI, the `prefill` mechanism, for a tier that needs a visible CLI session.
- Decision: All four fixed in v5.5.2. The strongest of them is the first, and it is deliberately the same shape as the courier-checks rule from v5.3.0: **the session never composes the launch, it runs the script or it prints.** No script on the project means no chaining yet — the `off` behaviour — and regeneration is a later maintenance touch.
- Alternatives considered: teaching a session to compose the launch safely (the `cd`, the three quoting layers, the receipt) — rejected, because that is the same argument the courier checks already lost: an inline composition is written fresh, at the end of a session running out of context, with nothing testing it. And letting a wrong window be corrected by killing and re-firing — rejected: it is what produced four windows, and the mechanics of killing another session were already measured and rejected in v5.4.0 (no cleanup, lane never released, orphaned lock guaranteed).
- Consequence: `start` on a project whose `scripts/keel-continue` predates v5.5.2 will still open in `$HOME` — the script is a project artifact and no skill release can retrofit it, so the reconciliation row asks for a regeneration and the MANIFEST names the `cd` as the change that matters. Two claims that pointed the same way as the fixes are worth keeping visible: the courier checks never catch a session that lands in `$HOME`, because they run on a hand-off file that session never reads; and a launch's exit code has never been evidence that a window appeared, which is why printing is the answer to every uncertainty and firing again is the answer to none.

## D-010 — The work never lives only on the developer's machine, and nothing stays uncommitted

- Date: 2026-07-31
- Context: The user raised a gap in the development flow that Keel had never stated: a project can be started, planned, specified and half-built entirely inside one folder on one computer, with no repository and no off-machine copy. Everything Keel produces — discovery, decisions, specs, code — would then exist in exactly one place. The related half is the same failure one step later: a repository whose work sits in the working tree, uncommitted, is invisible to every other checkout and survives nothing.
- Decision: A new UNBREAKABLE cross-cutting section in `SKILL.md` — "Work never lives only on this machine" — plus **Question 0** of the session-start setup batch (now four questions), a `Durability:` project-card line, the check at Phase 1 step 0a *before anything is created*, the same at adoption step 2, and two `scripts/keel-verify` checks: a remoteless repo with no recorded decision FAILS instead of being skipped, and a dirty working tree fails and names the files. Two things satisfy the requirement — a Git repository with a remote, or a tree that replicates off the machine (Dropbox and equivalents, confirmed with the user, never inferred from a folder name). A repo with no remote is explicitly a partial answer, not a pass. Commits go to `develop` or to a work branch bound for it, and a repo carrying only `main`/`master` gets `develop` created first.
- Alternatives considered: making it a Phase 7 hygiene item — rejected, since the loss it prevents happens during the months of work before a release, not at it. Making it advisory prose in the Git-flow section — rejected under this skill's own rule that a trap closed by prose alone is still open, hence the two mechanical checks. Blocking the project outright when nothing covers it — rejected: the user may legitimately accept the risk, so it is declinable, but only as a recorded D-entry with the consequence written out, never as a silence.
- Consequence: The one real cost is a question at the very start of a project, and it is paid once — the ANSWER is never re-asked, while the two facts behind it are re-verified every session with two cheap commands, so a removed remote surfaces the day it happens instead of the day it matters. Automatic mode is deliberately untouched: Keel performs `git init`, the first commit, the creation of `develop` and every commit and push itself without asking; only choosing WHERE the work is published stays the person's, because it is theirs to own. This change set is unreleased — the version, the `CHANGELOG` entry and `MANIFEST` Tables 2 and 3 wait for the user's explicit instruction per D-006 and the UNBREAKABLE version policy.

## D-012 — The continuation file is written at every sprint close, and kept current afterwards

- Date: 2026-07-31
- Context: The user asked whether the continuation prompt is actually produced at every sprint close, and stated the reason plainly: they want to shut the laptop when a sprint ends and know that a new chat, opened by hand later, needs only "read the continuation md". Reading the skill against that: the duty existed (Phase 5 §5 step 11) but was framed throughout as a SESSION-END artifact — "whenever the session is ending", "any session ending mid-work produced a continuation prompt", and the lock block's item 5 in the same words. In automatic mode a session normally carries straight on into the next sprint, so the close was precisely the case the wording did not compel.
- Decision: Make the sprint-close write UNCONDITIONAL and say so in the four places a session actually reads — `SKILL.md`, `references/project-state.md` (the file's own section, the template intro and the definition of done), `references/phase-5-development.md` (step 11 and the phase's definition of done), and the portability lock's item 5. It holds whatever `Autonomy:` and `Chaining:` say: chaining decides whether a next chat is OPENED, never whether the hand-off EXISTS.
- Alternatives considered: writing it only when the session actually stops — rejected, that is the status quo and it fails the exact case the user named. Committing the file so any machine can pick it up — rejected: it is per-machine ephemeral state whose freshness header is checked against THIS checkout, and v5.3.0 gitignored it for that reason.
- Consequence: The second half is what makes the first half true, and it is the part that was missing entirely. **A hand-off that is not current is worse than none**: the courier checks compare `Commit` and `Tree` against the repository, so a file written at a close and then left behind by three more slices returns `VERDICT: STOP` — it looks like insurance right up to the moment it is needed. A session that carries on therefore regenerates it at every commit point, and always before ending. The cost is one small overwrite per test point, against a reconstruction the mechanism exists to eliminate. **The lock block changed in substance for the second release running**, so `CLAUDE.md` and `AGENTS.md` need a real content refresh, not a restamp.

## D-013 — Reading the hand-off is the FIRST thing a resuming session does

- Date: 2026-07-31
- Context: D-012 guaranteed the file is always written and always current. The user pointed at the other half of the loop: for a bare "continua" to be enough, the arriving session has to READ it early, on its own, without being told where to look. Until now the fixed session-start order began at `docs/PROGRESS.md` and the hand-off was only consumed when someone pointed a session at it — which works when a chat is chained or the user pastes the instruction, and fails in exactly the case that matters, a chat opened by hand days later with a one-word prompt.
- Decision: `docs/continuation-prompt.md` is checked BEFORE the state files, in the Resume entry mode (`SKILL.md`), in the fixed session-start reading order (`references/project-state.md`) and in item 2 of the portability lock, so it holds for an assistant that opens the repo without the skill installed. If it exists, the session runs `scripts/keel-handoff-verify` and obeys the verdict; if it is absent, that is ordinary — it is gitignored, so a fresh clone has none — and the normal order proceeds.
- Alternatives considered: leaving it to the continuation prompt's own instructions — rejected, that is circular: the prompt cannot tell a session to read a file the session has not read. Making it an authority so the fresh chat could act on it alone — rejected, and the distinction is now written into all three places: the hand-off is a COURIER, `docs/PROGRESS.md` is the authority, and where they disagree the committed state wins.
- Consequence: One clarification was needed to make this safe rather than merely convenient. **`STOP` costs the FILE its authority, not the SESSION its work:** a stale or foreign hand-off is discarded, the session says so in one line and resumes from the committed state — the courier table already said this, but "the session stops on a `VERDICT: STOP`" was the phrasing carried in `SKILL.md`, and read alone it says the opposite. A session must never be paralysed by a courier it was free to ignore. Net effect: "continua" now boots the maintenance block, the setup, the hand-off and the state files in that order, and the work resumes at the exact position with no recap.

## D-015 — The forge sweep guards BOTH edges of a sprint, gated by a recorded interval

- Date: 2026-07-31
- Context: The after-sprint issue duty (v5.5.0) fires at the close and only at the close. Sprints are not adjacent in real life: days pass between one ending and the next being planned, and everything that arrives in that gap — a new report, or the comment on an `awaiting reporter` issue that decides whether it closes or reopens — waits for the NEXT close to be read. The sprint in between gets planned as if none of it existed, which is the most expensive moment to be uninformed.
- Decision: Add the same inbound sweep to the **sprint kickoff**, as step 1, ahead of plan mode and the re-validation, gated on freshness rather than run blindly: `docs/issues.md` gains a `Last inbound sweep:` header line stamped whenever any inbound sweep finishes (close or maintenance touch), and the project card's `Autonomy:` line gains `Issue sweep interval:` (default 24h, asked with the duty in the session-start setup batch). Missing or older than the interval → sweep before planning; within it → one line and move on.
- Alternatives considered: sweeping at every kickoff unconditionally — rejected, a sprint chained seconds after a close would re-read the forge for nothing, and a rule that visibly wastes work is a rule sessions start skipping. A fixed 24h with no card line — rejected: a project with a busy forge wants hours, a quiet one wants days, and the setup batch already asks the issue question, so the interval costs nothing to ask there. Making the kickoff sweep replace the close sweep — rejected: the close is where the outbound half (fix-landed comments, deploy notifications) belongs, and it is not symmetric with the kickoff.
- Consequence: The freshness stamp is what makes this mechanical instead of a memory of whether someone looked, and it is also what makes the chained case free. Existing projects add one card value and one header line; nothing migrates and the lock block is untouched, so v5.8.0 is the first release in three that needs only a stamp refresh of `CLAUDE.md` and `AGENTS.md`. Two structural defects in `MANIFEST.md` were found and fixed while placing the delta row — v5.7.0's Table 3 row had landed inside Table 2, and a blank line had split Table 3 since v5.4.1 — both of which broke a file that is read mechanically after every update.

## D-017 — The lane is released at the close-out, because "on exit" is a moment a session never reaches

- Date: 2026-07-31
- Context: Reported from a real project running `Chaining: start`. The closing session fired `scripts/keel-continue`, the launched window opened correctly, ran `scripts/keel-handoff-verify` as its first act, and stopped: `carril: OCUPADO`, the holder a live PID — the previous chat, sitting idle in its Terminal window, still holding the lane it had finished with. Every guard behaved exactly as specified. The chain did not fork, it deadlocked at link one, deterministically, and the only way out was the user closing a window nobody had told them to close. The single-lane lock said "the holder releases it on exit — every exit, including the failing ones", which cannot be performed by the party it names: the holder is a SESSION, and a session gets no callback when it ends; the PROCESS outlives it for as long as the window is open, which under `start` is forever.
- Decision: Release the lane at the **close-out** — a moment the session can act on — through `scripts/keel-handoff-verify --release`, which frees it only if the calling session is the recorded owner. Three enforcement points: `scripts/keel-continue` releases immediately BEFORE firing (contract point 7 — after the fire is a race the chain loses); the close-out runs it as its last act on EVERY path, `off` and `prefill` and blocked hand-offs included; and a BATON covers what neither can — `keel-continue` records its own PID in the launch receipt, so an arriving session that finds the lane held by the PID recorded as THIS hand-off's launcher takes it instead of stopping. Plus a busy-lane `STOP` that names the holder's PID, its start time and how to clear it.
- Alternatives considered: **Have the arriving session recover any live lane older than N minutes** — rejected: an age threshold is a guess about another session's state, and the case it would mis-handle is two sessions genuinely working in one tree, which is the outage the lane exists to prevent. **Have `keel-continue` take the lane and hand it over** — rejected: it re-introduces the exact self-block `--no-lane` was added to fix, and it puts the lock in the hands of the party the contract says can never know who else is in flight. **Have the closing session kill its own process after firing** — rejected outright: killing a process to free a lane is already forbidden for cause ("One launch per hand-off"), no cleanup runs, and it would destroy the user's window under them. **Only fix the `start` path** — rejected: the same wall stands in front of a chat the user opens by hand ten seconds after a close on an `off` project, which is the commonest continuation there is.
- Consequence: Two generated scripts change on every project whose card is not `Chaining: off`, at its next maintenance touch, and the close-out gains a final step everywhere. No new file, no card line, and the lock block is untouched — a stamp-only refresh. A lane already stuck on a project not yet regenerated is cleared by closing the previous chat's window or running `scripts/keel-handoff-verify --release` in it. The general lesson is worth more than the fix: **a duty written against a moment the actor never reaches reads as satisfied and is never performed** — "on exit" passed review three times because it sounds like diligence.

## D-019 — The recommended `Chaining:` value follows `Autonomy:` instead of being fixed at `off`

- Date: 2026-08-01
- Context: The user restated the standing autonomy rule: in automatic mode Keel must never stop while it can continue, must produce the continuation prompt AND open the continuation window, and stops only when a person's intervention is genuinely required. The stop rule and the hand-off contract already said all of this. What did not match was the recommendation attached to `Chaining:`, fixed at `off` on every project regardless of the card's `Autonomy:` line — so the ordinary automatic-mode setup ended each session by writing `docs/continuation-prompt.md`, showing it, and waiting for a person who by definition is not there. A hand-off nobody opens is a stop wearing the shape of a completed procedure.
- Decision: Make the recommendation conditional on `Autonomy:`. On `Autonomy: automatic` the recommended value is the maximum tier the project's gates allow — `start` where the four requirements are met, `prefill` otherwise; everywhere else it stays `off`. Recorded in `keel/SKILL.md`, `keel/references/project-state.md` (card line, `Chaining:` table, gating paragraph, question block) and `keel/references/phase-1-discovery.md` (card line, step 0a question).
- Alternatives considered: **Force `start` in automatic mode** — rejected: `start` moves development to CLI sessions and removes the only participant supervising the chain, and both facts belong to a decision the user makes per project, not to a default. **Relax one of the four gates so automatic projects reach `start` more often** — rejected: the gates were each written from a measured failure (a forked chain, a headless launch that opens nothing, a permission prompt at every link, a missing binary), and a recommendation is not a reason to un-learn them. **Leave it and rely on the stop rule alone** — rejected: that is the state that produced the gap; the stop rule governs what happens inside a session and says nothing about whether a next one opens.
- Consequence: No new file, no new card line, no migration, and the lock block changes only its stamp. One per-project action, only where it applies: on an existing project whose card says `Autonomy: automatic` and `Chaining: off`, re-ask the chaining question once with the new recommendation.
